## 2. 阻断级发现

### P0-01 审核记录和审核队列存在越权读取

- `src/collections/ListingReviews.ts:34-38` 将审核记录读取权限设为 `read: () => true`。该集合包含提交快照、驳回原因、提交人和审核人。
- `src/components/admin/ListingReviewQueue.tsx:51-72` 使用 `overrideAccess: true` 读取最多 200 条待审核房源和 2000 条审核历史，未按当前用户的数据范围过滤。
- 页面只用 `canReview` 隐藏操作按钮，但无审核权限不等于可以读取全量审核数据。

影响：普通登录用户乃至公开 API 调用者可能读取不应可见的审核数据；违反服务端权限和数据范围约束。

修复要求：

1. 为 `listing-reviews` 建立基于登录、操作权限和城市/组织范围的读取条件。
2. 队列查询必须继承当前请求权限或显式拼接数据范围，禁止用 `overrideAccess` 作为展示查询捷径。
3. 增加匿名、跨城市、无审核权限、管理员四类集成测试。

### P0-02 “审核通过后上架”不是原子操作

- `src/components/admin/ListingReviewQueueClient.tsx:166-184` 先调用审核接口，再调用发布接口。
- 第二个请求失败时，代码明确保留“已通过但未上架”状态。

影响：与“审核 + 上架必须在同一事务中完成”的产品规则冲突，且会产生半成功状态。

修复要求：提供单一服务端命令，例如 `approve_and_publish`，在一个数据库事务内完成状态校验、审核记录、发布状态变更、审计日志和领域事件写入；任一步失败整体回滚。

### P0-03 高风险操作的“业务 + 审计同事务”并未成立

- `src/domain/audit/with-audit.ts` 先执行业务函数，再尝试写审计。
- 审计失败时虽然向调用方抛错，但业务写入已经发生，代码没有启动、传递或回滚真实数据库事务。

影响：调用方会看到失败响应，但数据可能已改变；审核、发布等高风险操作失去审计完整性保证。

修复要求：使用 Payload/数据库适配器支持的真实事务会话，业务写入、审核记录、审计日志和 outbox 事件必须共享同一事务；增加“审计写入故障后业务数据不变”的数据库集成测试。

### P1-08 SQLite schema 自动同步不是幂等启动

浏览器访问 `http://localhost:3717/` 返回 500，错误为：

`SQLITE_ERROR: index payload_locked_documents_rels_order_idx already exists`

干净重启后首页、列表、房源详情和楼盘详情均可访问，因此不是持续性不可用；但首次请求曾返回 HTTP 500，说明 schema 初始化存在竞争或幂等缺陷。

影响：并发初始化、首次部署或开发环境重启可能出现瞬态 500，且 SQLite 模式不能判断 16 个代码迁移的应用状态。

修复要求：先备份数据库，查明自动 schema push 与迁移历史冲突的来源，提供可重复的 SQLite 恢复步骤；随后在全新数据库和现有数据副本上分别执行多次启动、迁移和数据审计。

## 3. 高优先级发现

### P1-01 审核流缺少真正的任务认领和职责隔离

`src/endpoints/listing-review-decision-endpoint.ts` 对提交、撤回、通过、驳回统一使用 `listing:review` 权限；当前模型以追加事件模拟 task status，但没有独立的待处理任务、认领人、认领时间和并发认领约束。

缺失能力包括：

- 提交者与审核者职责分离；
- 禁止自审及受限下属关系审核；
- 撤回仅限原提交者且仅在未认领前；
- 待处理 → 处理中 → 已完成/已取消的真实任务状态；
- 两名审核人并发操作时的 claim / version 冲突处理。

### P1-02 有效供给列表被候选上限截断，分页、排序和总数不可信

- `src/domain/public-catalog/supply-adapter.ts:137-138` 固定候选上限 500。
- `src/domain/public-catalog/supply-adapter.ts:265-274` 实际只取 `pageSize * 5` 条候选，再由 Facade 内存排序分页。
- `src/domain/public-catalog/facade.ts` 的总数、总页数和排序只针对这批候选。

影响：

- 默认每页 24 条时，最多只看见 120 条候选；
- “价格升序/降序”“最新”等不是全量稳定排序；
- 高页码永远无法正确返回；
- facet 和 total 可能严重偏小。

修复要求：把可数据库表达的条件与排序下推到数据库；对必须精筛的条件采用可继续游标/分批扫描，直到填满目标页并获得可信计数，或建设物化有效供给索引。

### P1-03 举报暂停查询在 1000 条后静默放行

`src/domain/review/effective-supply.ts:198-208` 只取 1000 条 `supplyPaused=true` 记录且不分页。

影响：超过上限的暂停房源会重新进入公开供给，属于 fail-open。

修复要求：按目标房源关联查询、分页穷尽，或把暂停状态投影到可索引的供给读模型；任何查询异常应 fail-closed。

### P1-04 sitemap 天然不完整

`src/app/(frontend)/sitemap.ts:30-39`：

- 房源复用默认搜索输入，受 120 条候选限制；
- 楼盘固定 `limit: 200`；
- 内容页固定 `limit: 500`；
- 均无分页或 sitemap 分片。

影响：规模超过上限时合法公开页面不会被搜索引擎发现。

### P1-05 有效媒体检查只数数组长度

`src/domain/review/effective-supply-snapshot.ts:28-53` 使用 `gallery.length` 作为有效媒体数，没有验证关联媒体存在、可读、未删除且 URL 可用。

影响：3 个空壳/失效媒体关系也会通过有效供给门槛。

### P1-06 商户关系取值可能误判

`src/domain/review/effective-supply-snapshot.ts:60-82` 只按 `-effectiveFrom` 取最近一条关系，然后在内存判断时点。若最新记录尚未生效，而更早关系在当前时点仍有效，会错误排除有效房源。

此外，商户资格来自 `listing.merchant` 快照，而有效期来自关系表，代码没有证明两者一定指向同一商户。

修复要求：查询直接包含 `effectiveFrom <= asOf` 与 `effectiveTo > asOf / null`，并从命中的关系加载商户资格；不要混用 listing 快照和关系事实。

### P1-07 审核台完整度对商户关系硬编码为有效

`src/components/admin/ListingReviewQueue.tsx:90-111` 将 `hasValidMerchantRelation` 固定为 `true`。

影响：提交后关系失效、商户停用或资格过期时，审核台仍显示完整，审核人无法识别当前事实变化。

## 4. 中优先级发现

### P2-01 移动端“查看 N 套”不是暂存条件结果

`src/components/frontend/MobileFilterDrawer.tsx:24-25, 389` 使用服务端传入的“已应用条件” `totalDocs`。用户在抽屉中修改暂存条件后，N 不会随新条件变化，与任务 3.4 的描述不一致。

### P2-02 埋点只有 DOM 标记，没有采集闭环

F3.6、F4.6 的证据明确写着等待 F6 SDK。`data-event-name` 只是钩子，不是可验证的事件采集、去重、隐私过滤和失败处理实现，因此不能标记任务完成。

### P2-03 F3/F4 手工 E2E 未执行

F4.7 的文档只写“可启动”“建议覆盖”，没有测试日期、环境、路径、截图或结果。此次实际启动又被 P0-04 阻断。

### P2-04 React Hook lint 规则被压制

`src/components/admin/ListingReviewQueueClient.tsx:287-289` 禁用了 `react-hooks/exhaustive-deps`。`handleApprove` 捕获 `publishAfterApprove` 等状态，依赖数组不完整会产生陈旧闭包风险。

### P2-05 缓存标签文档自相矛盾

`src/domain/public-catalog/cache-tags.ts:94` 声称 `revalidateTag` 支持前缀/通配，`102-103` 又声称不支持。实现应只依赖明确、已测试的精确标签，不应把注释当作一致性保障。

### P2-06 详情页存在内容呈现缺陷

浏览器走查发现房源详情重复输出两个二级标题“房源说明”，且“可入驻”直接显示 ISO 时间 `2026-08-15T00:00:00.000Z`，没有按中文日期格式呈现。
