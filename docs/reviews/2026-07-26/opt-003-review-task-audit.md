# OPT-003 审核任务认领与职责隔离审查

> 结论：未完成。当前 `listing-reviews` 是事件流，不是可安全认领的任务模型。

## 发现

1. `ListingReviews` 的事件记录包含 `taskStatus`，但记录设计为 append-only；系统没有一个可原子更新的“当前任务”，因此无法实现真正的 claim、释放、超时和并发冲突。
2. 审核接口没有验证任务认领人、提交人自审、上下级隔离和操作责任边界，仅依赖统一的 `listing:review` 操作权限。
3. 任务版本校验可选且存在“先读后写”的竞态；多个审核人可能同时通过前置检查。
4. 若直接通过 Collection API 创建审核记录，服务端保护钩子不会替代完整的身份、数据范围及命令授权。OPT-001 已先将外部 create/update/delete 全部关闭。
5. 项目虽有 Tasks 相关结构，但审核流程未真正接入；现有 claim 逻辑也未证明具备原子更新及城市范围约束。

## 建议模型

建立独立 `review-tasks` 当前态集合，至少包含：

- `listing`、`status`、`assignee`、`claimedAt`、`submittedBy`
- `city` 或可稳定索引的数据范围键
- `listingVersion`、`taskVersion`
- 唯一的活动任务约束

`listing-reviews` 继续只承担不可变事件历史，不再充当任务当前态。

## 命令与权限

1. `claim`：仅有审核菜单、审核操作权限且命中城市范围的 OPS/ADM 可执行；以 `status=open + taskVersion` 为条件原子更新。
2. `approve/reject`：必须由当前 assignee 执行；禁止提交人审核自己的房源；同时校验任务版本和房源版本。
3. `withdraw`：只允许提交者或明确授权角色执行，并校验任务尚未完成。
4. 每个命令采用独立、最小权限标识，不再以单一 `listing:review` 覆盖全部动作。
5. 所有成功命令由 OPT-002 的事务执行器统一写入任务当前态、房源状态、审核事件、领域事件和审计。

## 最低验收测试

- 两名审核人并发 claim，仅一人成功，另一人返回 409。
- 未认领、非认领人、跨城市、无菜单、无操作权限均被服务端拒绝。
- 提交人自审、下属/同组职责冲突按 PRD 被拒绝。
- 已完成或已取消任务不能再次 claim、审核或撤回。
- 任务版本或房源版本过期时不产生任何业务、事件或成功审计写入。
