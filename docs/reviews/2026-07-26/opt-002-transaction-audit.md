# OPT-002 审核、发布与审计事务审查

> 结论：未完成，存在 P0 数据一致性风险，暂不可按 PRD 验收通过。

## 发现

1. `src/domain/audit/with-audit.ts` 仅按“业务写入 → 审计写入”的顺序执行，没有调用 Payload 数据库适配器的 `initTransaction`、`commitTransaction`、`killTransaction`。审计失败时业务数据可能已经落库，抛错不会自动回滚。
2. “审核通过并发布”由审核与发布两次请求组成，不是一个原子操作。任一请求失败会留下中间状态。
3. 审核、发布路径没有与业务状态同事务写入可消费的领域事件，无法满足 PRD 中“业务数据 + 审计 + 事件”的一致提交要求。
4. `expectedVersion` 不是所有高风险写入的必填条件，且当前“先读版本、后更新”的校验存在 TOCTOU 窗口，不能阻止并发覆盖。
5. 审计动作名称与业务动作没有形成完整的一一对应，失败审计还可能重复写入。

## 修复方案

1. 建立单一事务执行器：复用请求事务 ID，在事务内完成业务更新、审核事件、领域事件和成功审计；任一步失败统一回滚。
2. 将“审核通过并发布”收敛为一个服务端命令，或明确拆为两个各自原子的命令并禁止客户端假定整体成功。
3. 对高风险命令强制 `expectedVersion`，使用带旧版本条件的原子更新；更新行数为 0 时返回 `409 VERSION_CONFLICT`。
4. 失败审计在主事务回滚后独立写入，只记录一次，并明确它不代表业务提交成功。
5. 所有 Local API 写入显式透传同一个 `req`/事务上下文，禁止事务内调用脱离请求的 Payload 实例。

## 最低验收测试

- 业务更新、审核事件、领域事件、成功审计任一步注入故障时，数据库业务状态完全不变。
- 两个并发请求携带相同 `expectedVersion` 时仅一个成功，另一个稳定返回 409。
- 审核通过并发布的所有状态、事件与审计要么全部存在，要么全部不存在。
- 失败路径只产生一条失败审计，且不产生成功审计或领域事件。
- 使用真实 SQLite/PostgreSQL 适配器运行集成测试，不能仅以 mock 调用次数作为事务证据。
