## 执行证据

定向执行 `effective-supply`、`report-supply-pause`、`public-catalog-effective-supply-consistency`、`building-aggregate` 和生产等价性等测试。

结果：6 个测试文件、118 个测试通过。测试主要验证小样本规则和模块调用关系，没有覆盖本阶段要求的 1000+ 数据、深分页、全局排序、暂停查询异常及关系切换时点。

## [P0] OPT-006：举报暂停查询截断会使房源重新公开

`getPausedListingIds()` 固定 `limit: 1000`，没有分页，也没有检查 `hasNextPage`/`totalPages`。第 1001 条及之后的暂停房源不会进入 `not_in` 集合，会被公开目录、楼盘聚合、咨询候选等消费者重新视为有效供给。

这是 fail-open 安全问题，不能以“异常规模需人工处理”作为正确性兜底。

建议：

1. 优先将暂停状态改为可直接数据库联结/反连接的持久化当前态，避免超长 `not_in`。
2. 若短期保留查询集合，必须完整分页；任一分页失败时整个有效供给查询 fail-closed。
3. 增加 1001/2001 条暂停记录、分页中途异常、重复 listing ID 和空目标 ID 的真实适配器测试。

## [P1] OPT-005：候选截断破坏 total、分页和全局排序

`findEffectiveListings()` 只读取 `min(pageSize × 5, 500)` 条候选，且未按用户要求的排序在数据库侧获取全局候选。Facade 随后只对这批样本精筛、排序和分页。

因此 `totalDocs` 不是真实总数，深分页会提前出现空页，价格/面积/更新时间排序只在样本内成立；精筛淘汰率较高时，首屏也可能缺数据。`computeBuildingSupplyAggregate()` 固定最多 500 条，套数、总面积和价格区间同样会截断。

建议：

1. 将可查询条件下推数据库，对剩余条件采用稳定游标分批精筛，直到填满目标页并确认总量。
2. total 使用物化有效供给当前态或可完整扫描的异步索引，不能从固定样本推导。
3. 排序在数据库/索引层统一执行，并用不可变 ID 作为稳定次序键。
4. 增加至少 1500 条数据、淘汰率高于 80%、深分页和同值稳定排序测试。

## [P1] OPT-007：商户关系、商户资格与 asOf 不是同一事实

精筛直接从 `listing.merchant` 读取商户资格；关系查询只读取同房源 `effectiveFrom` 最新的一条记录，并不按 `asOf` 过滤，也不读取该关系关联的 merchant。

最新关系在 `asOf` 之后开始时，历史有效关系会被忽略；Listing merchant 与当前关系 merchant 不一致时，关系有效期来自 A、资格来自 B，形成不存在的混合快照。

建议：

1. 以同一个 `asOf` 查询 `effectiveFrom <= asOf` 且 `effectiveTo` 为空或 `> asOf` 的唯一关系。
2. 从命中的关系读取 merchant，并解析同一商户的状态、资质和服务城市。
3. 命中 0 条时 fail-closed；命中多条时视为完整性错误、fail-closed 并告警。
4. 增加相邻边界 `t=effectiveTo`、历史 asOf、未来关系、重叠关系及冗余 merchant 不一致测试。

## [P1] OPT-008：sitemap 固定上限导致 URL 静默丢失

sitemap 的房源复用默认候选上限，楼盘固定 `limit: 200`，内容页固定 `limit: 500`。超过上限后不会分页或生成 sitemap index。当前测试只检查是否调用统一接口，没有验证 URL 集合完整。

建议：

1. 使用 Next.js sitemap 分片能力或 sitemap index。
2. 每种资源按稳定 ID/更新时间分页读取至末页，禁止依赖默认 limit。
3. sitemap 房源资格继续复用统一有效供给当前态。
4. 增加 50,001+ URL 分片、边界无重复无遗漏、失效供给撤销及资源超限测试。
