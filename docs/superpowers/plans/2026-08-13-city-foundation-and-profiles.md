# City Foundation and Profiles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add database-driven City Site Profiles and a cached, fail-closed `CityContext` resolver that all later frontend work can consume.

**Architecture:** Keep geographic truth in `locations` and frontend operations content in a one-to-one `city-site-profiles` Collection. A domain resolver validates unknown slugs, queries only canonical active cities, maps a read-only public DTO, and is wrapped by request-level `React.cache()` plus per-city `unstable_cache` factories.

**Tech Stack:** Payload CMS 3.86, PostgreSQL, Next.js 16.2, React 19.2, TypeScript, Vitest, pnpm on Node.js 22.

## Global Constraints

- Follow the master constraints in `docs/superpowers/plans/2026-08-13-multi-city-frontend-implementation-index.md`.
- Re-read `payload-office-platform/AGENTS.md`, `.agent/core.md`, `.agent/backend.md`, `.agent/frontend.md`, `.agent/migrations.md`, and `.agent/testing.md` before Task 1.
- Profile reads are public DTO reads; profile writes require `location:manage`; delete is disabled.
- A city with any profile has an immutable slug. Do not implement `previousSlugs`.
- The schema migration body must be generated by Payload and not hand-edited.
- Seed profiles by immutable code: Shanghai canonical `LEGACY_LOC_1`; Hangzhou `CITY-HZ`; Suzhou `CITY-SZ`; Jiaxing `CITY-JX`; Nanjing `CITY-NJ`; Wuxi `CITY-WX`; Ningbo `CITY-NB`.
