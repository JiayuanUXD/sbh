# 公开站性能快速优化设计

> 日期：2026-08-07  
> 状态：待书面评审  
> 范围：低风险、高收益的公开站查询缓存、预取控制、请求去重与首页媒体降载

## 1. 背景

生产模式走查发现：首页、房源列表、房源详情和 sitemap 存在相似的重复查询或加载放大问题：

- `/listings` 每次请求都执行完整有效房源搜索，并额外调用 `getHomepage`，只为取得区域选项；
- 首页多个筛选入口使用 Next.js 默认预取，滚动后会自动触发大量昂贵的 RSC 搜索请求；
- 首页仍直接执行 `getHomepage`，没有使用已经存在的标签缓存封装；
- `/sitemap.xml` 每次请求都重新读取房源、楼盘和内容页；
- 房源详情的 metadata、页面和推荐会重复读取当前房源，且后续数据串行加载；
- 首页首屏自动下载约 1.2 MB 的背景视频，包括不需要动效或希望节省流量的设备。

当前稳态测量中，首页约 0.54 秒、房源列表约 1.2 秒、sitemap 约 1.2 秒；缓存后的楼盘列表已能稳定在毫秒级，证明标签缓存路径适合本轮快速优化。

## 2. 目标

在不修改数据库结构、不改变统一有效供给谓词的前提下：

1. 让重复访问首页、房源列表、详情和 sitemap 命中最长 5 分钟的标签缓存；
2. 消除房源列表对完整首页聚合的依赖；
3. 阻止筛选链接默认预取造成的查询放大；
4. 减少详情页同一请求中的重复读取和串行等待；
5. 避免不适合播放视频的客户端下载首页背景视频；
6. 保持供给、楼盘、文章和内容页变更后的可控失效窗口。

## 3. 非目标

- 不在本轮重写数据库级有效房源分页、计数和排序；
- 不移除 `findEffectiveListings` 当前最多 1000 条候选的上限；
- 不改变搜索结果、facet、排序、分页或统一有效供给的业务口径；
- 不修改 Collection 字段、索引、约束或数据库迁移；
- 不引入 Cache Components、外部缓存服务或新的客户端状态库；
- 不优化后台登录或后台业务页面。

数据库级有效房源分页另立后续任务，必须包含 PostgreSQL 专项验证和回滚方案。

## 4. 方案比较

### 方案 A：现有 `unstable_cache` + 标签失效 + 选择性请求去重（采用）

复用 `cached-queries.ts` 和现有供给事件失效体系，为公开查询增加 300 秒兜底过期；内容集合通过 Payload Hook 主动失效。筛选入口关闭自动预取，详情再用并行加载和请求内复用降低重复读取。

优点是改动集中、与现有架构一致、无迁移，并能显著改善重复访问。限制是首次冷搜索仍受当前候选扫描实现约束。

### 方案 B：仅使用 React 请求内 `cache`

可以减少单次渲染中的重复读取，但无法改善不同请求或客户端导航之间的 1 秒级搜索，也无法解决 sitemap 重复查询和预取放大，因此不足以单独采用。

### 方案 C：整页静态化或启用 Cache Components

理论上可获得更强的页面级缓存，但会扩大路由、动态搜索参数和内容失效的改造范围，也会提高本轮回归风险。留作框架级后续演进，不纳入快速优化。

## 5. 子项目与顺序

为遵守单任务编号和 3–8 个核心文件的边界，本设计分为三个顺序执行、独立验证的任务：

1. **OPT-026 房源列表查询与预取优化**：列表缓存、轻量区域选项、筛选入口预取控制；
2. **OPT-027 首页与 sitemap 缓存失效**：首页缓存、文章/内容页 Hook、sitemap 缓存；
3. **OPT-028 详情请求与首页媒体降载**：详情缓存/并行加载、视频封面和按需加载。

每个任务单独建立 Task Packet、失败测试和验证证据。前一任务验证通过后再激活后一任务。

## 6. OPT-026：房源列表查询与预取优化

### 6.1 数据流

`/listings` 先解析并规范化 URL 参数，以 canonical query 和完整搜索输入调用 `getCachedSearchListings`。缓存 key 同时包含规范化查询和输入，缓存标签至少包含 listings、facets、home 和 sitemap 类别标签，最长 300 秒重新验证。

区域选项不再通过 `getHomepage` 获取。Public Catalog 新增轻量只读入口，仅调用 `SupplyAdapter.findEffectiveDistricts` 并映射成现有 `DistrictViewModel`，不执行精选房源、在租面积聚合、楼盘和文章查询。该结果使用区域/楼盘相关标签缓存 300 秒。

### 6.2 预取策略

以下会产生高基数或昂贵搜索请求的链接显式设置 `prefetch={false}`：

- 首页办公类型和热门区域入口；
- 导航中的预设房源筛选入口；
- 房源列表筛选 chip 和分页链接。

普通内容、楼盘和具体详情链接保留默认行为，避免全站禁用预取。

### 6.3 正确性

- URL、canonical、筛选恢复和分页行为不变；
- 区域选项仍只来自启用且公开有效的位置，不从当前页结果反推；
- 缓存只包装统一 Public Catalog 查询，不复制或放宽有效供给谓词；
- 供给和位置相关事件继续失效类别级标签，300 秒为最后兜底而不是主要一致性机制。

## 7. OPT-027：首页与 sitemap 缓存失效

### 7.1 首页

首页改用 `getCachedHomepage`，并为封装增加 `revalidate: 300`。Listing、Building、区域、商户资格等供给事件继续通过现有 `cache-invalidator` 失效 home/listings/facets 标签。

Articles 新增轻量 Hook：文章新增、修改、发布、撤回、软删除或恢复后失效 `public:home:shanghai`。Hook 失败记录结构化错误，不阻断 CMS 写入；300 秒过期保证缓存不会无限陈旧。

### 7.2 Sitemap

`sitemap.ts` 保持运行时生成，但将昂贵的数据装载封装进 `unstable_cache`：

- 缓存标签包含 sitemap、listings、buildings 和 pages 类别；
- 最长缓存 300 秒；
- URL 映射和 `lastModified` 继续使用同一公开 DTO/文档结果；
- 页面本身不缓存当前时间戳等无关动态数据，主要避免重复数据库读取。

Pages 新增变更/删除 Hook，失效 pages 类别和 sitemap 标签。Collection 字段不变，因此无需生成迁移；因 Collection 配置改变，按项目规则重新生成 Payload 类型并验证无意外差异。

## 8. OPT-028：详情请求与首页媒体降载

### 8.1 房源详情

metadata 和页面统一使用缓存的 slug 查询；相关推荐增加与 listings/buildings 标签关联的缓存封装。取得当前房源后，楼盘详情、推荐、周边 POI 和服务时间改为并行等待。

该方案降低重复访问和串行延迟，但不在本轮重构推荐算法内部的冷请求重复读取。详情输出仍依赖统一有效供给查询，相关供给事件负责及时撤销缓存。

### 8.2 Hero 视频

从现有视频生成静态 WebP 封面，作为首屏稳定背景和视频 `poster`：

- 移动端不装载视频资源；
- `prefers-reduced-motion: reduce` 或浏览器 `saveData` 生效时不装载视频；
- 其他桌面环境在页面空闲后再设置视频源并播放；
- 播放失败时继续展示封面，不影响搜索和咨询入口；
- 保持视频静音、循环、行内播放，不新增自动轮播。

客户端组件只承担媒体能力检测与延迟装载，不承载业务数据或页面状态。

## 9. 错误处理与可观测性

- 查询失败仍进入现有页面错误边界，不把失败伪装成空结果；
- 缓存封装不捕获并吞掉 Public Catalog 错误；
- 内容失效 Hook 记录 collection、operation 和 tag，不记录正文、用户信息或其他 PII；
- Hook 失效失败不回滚已成功的内容写入，依赖 300 秒兜底过期，并保留错误日志供监控；
- 视频能力检测或播放失败静默回退为封面，不产生阻塞式错误 UI。

## 10. 测试与验收

每个子任务先建立失败测试，再做最小实现。

### 10.1 自动化

- 合约测试：目标路由使用缓存封装，缓存均声明正确 tags 和 300 秒上限；
- 单元测试：区域选项只调用有效区域查询；文章/页面 Hook 触发正确失效标签；
- 回归测试：统一有效供给排除集合、筛选 URL、排序、分页、metadata 和 sitemap 内容不变；
- 媒体测试：移动端、减少动效和节省流量路径不会设置视频源；
- `pnpm exec payload generate:types`（Collection 配置任务）、`pnpm exec tsc --noEmit --pretty false`、相关测试、完整测试和 `pnpm build`。

### 10.2 浏览器与性能

使用 Node 22 生产构建和真实浏览器验证：

- 视口：375×812、768×1024、1440×900、1920×1080；
- 路由：首页、房源列表默认/筛选/分页、房源详情、sitemap，以及至少一个相邻页面；
- 控制台无新增错误；键盘筛选和分页可用；
- 首页滚动后不再自动产生大批筛选列表 RSC 请求；
- 缓存命中后：首页、列表和 sitemap 服务端响应目标 200–300 ms 内；
- 缓存命中的列表客户端跳转目标 500 ms 内；
- 移动端与减少动效路径不请求 `/hero/bg.mp4`。

性能目标是本地等价环境的回归门，不声称等同线上 p75。首次冷列表查询预计仍接近当前约 1 秒，直至数据库级分页任务完成。

## 11. 风险与回滚

- **陈旧数据风险**：通过既有供给事件、内容 Hook 和 300 秒过期三层控制；
- **缓存 key 漂移**：只使用 canonical query 与解析后的确定性输入，并用测试覆盖参数顺序；
- **失效 Hook 运行上下文**：通过 mock `next/cache` 集成测试和实际 CMS/浏览器验证确认；
- **自动预取减少后的交互变化**：目标链接点击时仍正常导航，只取消后台抢跑；
- **视频兼容性**：封面始终存在，按需视频属于渐进增强。

任一子任务可通过恢复对应路由直连查询、移除新增 Hook 或恢复原视频标签独立回滚，不涉及数据回滚。
