# 首页访问楼盘列表性能优化设计

## 背景与根因

用户从首页进入 `/buildings` 时，服务端首字节时间稳定在约 1.2 秒。楼盘列表路由当前声明 `force-dynamic`，每次请求都直接调用 `searchBuildings`：先读取全部有效楼盘，再执行一次全量有效供给聚合 SQL 计算每个楼盘的在租面积，最后才在内存中筛选并切出当前页。

针对当前本地数据的分段测量结果：

- 热态楼盘基础读取约 21–22ms。
- 在租面积聚合约 818–834ms。
- 聚合 SQL 是热态请求的主要耗时，不是首页链接、React 渲染或图片加载。
- 当前公开楼盘仅 26 个，把筛选和分页整体下推数据库会扩大改动面，但不能消除每次请求重复计算相同聚合结果的问题。

项目已有基于 Next.js `unstable_cache` 和领域事件 `revalidateTag` 的公开目录缓存体系，首页、详情页和房源搜索已有对应封装；楼盘搜索尚未接入。

## 方案

在 `src/lib/frontend/cached-queries.ts` 增加楼盘搜索缓存封装，并让 `/buildings` 页面改用该封装：

1. 缓存函数内部使用默认公开搜索上下文调用 `searchBuildings`，不改变 Public Catalog Facade 和 SupplyAdapter 的职责。
2. 使用固定缓存键区分楼盘搜索结果；当前查询没有业务入参，页面的区域、等级和分页仍基于同一份完整 DTO 在内存完成。
3. 同时绑定 `public:buildings` 与 `public:listings` 类别标签。楼盘字段变化依赖前者，在租面积及有效供给变化依赖后者。
4. 设置 `revalidate: 300` 作为最长五分钟的兜底刷新，符合前台公开供给缓存上限，也覆盖领域事件缺少楼盘标识或未进入消费链的异常情况。
5. 保留路由的 URL 筛选、分页、Metadata、空状态和 `force-dynamic` 行为；仅复用昂贵查询结果，避免改变页面语义。

首页中的 Next.js `Link` 在生产环境可预取目标路由；缓存命中后，后续首页跳转、分页和筛选不会重复执行约 0.82 秒的聚合 SQL。首次冷请求仍需生成一次结果，但最长每五分钟或相关领域事件后才重新生成。

## 缓存一致性

楼盘搜索结果包含两类数据：

- 楼盘自身字段、启停状态、区域和等级。
- 从有效房源聚合出的在租面积。

因此缓存必须同时依赖楼盘和房源类别标签，不能只标记 `public:buildings`。现有 `computeAffectedTags` 会在房源发布、撤销、审核和举报供给变化时失效 `public:listings`；事件携带楼盘 ID 时还会失效 `public:buildings`。五分钟兜底时间负责限制未被事件覆盖的楼盘字段变化所产生的陈旧窗口。

本次不修改失效事件模型，也不扩大到楼盘详情或房源列表的其他缓存路径。

## 测试与验收

按测试驱动方式实施：

1. 增加缓存合同测试，要求楼盘搜索封装调用 `searchBuildings`、同时声明两个类别标签，并设置 300 秒重新验证。
2. 增加页面接入合同测试，要求 `/buildings` 使用缓存封装，且不再直接调用 `searchBuildings` 或创建搜索上下文。
3. 运行新增测试、公开目录缓存相关测试、TypeScript 检查和生产构建。
4. 在真实浏览器验证首页进入楼盘列表、楼盘筛选或分页、一个相邻前台路由及控制台。
5. 使用连续 HTTP 请求记录优化前后 TTFB；验收重点是缓存命中请求不再重复承担约 0.82 秒聚合耗时，且页面数据、筛选和分页结果不变。

## 非目标

- 不重写有效供给 SQL，不增加数据库索引或物化视图。
- 不把筛选、排序和分页接口下推到数据库。
- 不移除楼盘卡片的在租面积。
- 不改变视觉、路由参数、SEO、权限或公开 DTO。
- 不修改 Collection、迁移或生产数据。

## 风险与回滚

主要风险是缓存标签不完整导致在租面积或楼盘信息短暂陈旧。双类别标签保证已覆盖事件即时失效，300 秒过期把其他情况限制在前台规范允许的五分钟内。

回滚只需让楼盘列表恢复直接调用 `searchBuildings`，并删除新增缓存封装和测试；不涉及数据库、迁移或数据恢复。
