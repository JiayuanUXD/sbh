# 后台登录后工作台性能优化设计

## 背景与目标

登录接口本身约 138ms；登录后的 `/admin` 首次服务端渲染约 23.5s。根因是 Dashboard 统计组件读取最多 500 条候选房源后，逐条串行查询有效商户关系。目标是让后台框架不再等待统计完成，并将有效供给计算从 N+1 收敛为批量查询，同时保持前台、预览、聚合和 Dashboard 的统一有效供给口径。

## 方案

1. 在 `effective-supply-snapshot` 提供共享的批量关系加载与批量有效供给判定。一次查询候选房源，一次查询候选房源当前生效关系；按房源 ID 分组，零条或多条关系均 fail-closed。
2. 抽出 `dashboard-stats` 服务，运行现有 7 个轻量 count 与批量有效供给统计，并返回 Dashboard 当前需要的稳定 DTO。
3. 新增仅登录用户可访问的 `GET /api/dashboard-stats`。单个请求使用同一个 Payload request，权限仍由服务端执行。
4. Payload Widget 服务端只渲染一个客户端加载器；客户端显示骨架，异步请求统计接口，成功后渲染现有 `DashboardOverview`，失败时提供错误态和重试按钮。这样统计不阻塞 `/admin` HTML。

## 边界与风险

- 不改变有效供给业务谓词、权限范围、Dashboard 文案或下钻链接。
- 不引入缓存、预聚合、数据迁移或新依赖。
- 批量关系查询使用 `depth: 1`，避免反向展开完整房源；保持“恰好一条当前有效关系”的不变量。
- 候选上限仍为 500，本任务只修复查询形态与阻塞体验，不改变历史统计口径。

## 验收

- 500 个候选仅触发一次 `listing-merchant-relations` 查询。
- 重叠关系继续判为无效供给。
- `/admin` 服务端渲染不执行统计数据库查询。
- 登录态接口返回现有 Dashboard 所需 8 个数值；未登录返回 401。
- 相关单测、全量测试、类型检查、构建通过；浏览器验证骨架、成功态、错误态及控制台。
