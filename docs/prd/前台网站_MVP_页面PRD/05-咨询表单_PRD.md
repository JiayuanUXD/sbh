# FP-05 咨询表单 PRD

> 形态：跨页面弹层/移动端抽屉  
> 优先级：P0  
> 状态：待确认

## 1. 模块目标

咨询表单应以尽可能低的填写负担收集可跟进、可归因且经过明确同意的选址需求，同时避免重复线索、垃圾请求和个人信息泄露。

## 2. 入口

- 首页“获取选址方案”。
- 首页收束咨询模块。
- 房源详情“询价 / 预约看房”。
- 楼盘详情“咨询该楼盘”。
- 房源列表无结果状态“提交需求”。
- 内容页文末 CTA。

入口必须携带页面类型、页面路径、目标房源/楼盘和白名单化活动参数。

## 3. 表单字段

### 3.1 必填

- 姓名：1–50 个可见字符。
- 手机号：中国大陆手机号作为 MVP 主规则，提交前统一去空格和分隔符。
- 隐私政策同意：必须主动勾选，记录政策版本。

### 3.2 选填

- 公司名称：最多 100 字符。
- 留言：最多 1,000 字符。
- 意向区域。
- 预算。
- 需求面积。
- 计划入驻时间。

房源详情入口默认展示目标房源摘要；楼盘入口展示目标楼盘摘要。用户无需重复填写目标名称。

## 4. 交互流程

1. 打开表单并将焦点移至标题或首个输入框。
2. 用户填写并同意隐私政策。
3. 客户端只做即时体验校验，服务端执行最终校验。
4. 提交按钮进入不可重复点击状态。
5. 成功后显示“已收到需求”和预期后续动作。
6. 关闭后返回原页面与原滚动位置。

移动端使用底部抽屉或全屏表单；键盘弹起时提交按钮和当前字段不得被遮挡。

## 5. 服务端业务规则

- 请求 body 作为 `unknown` 进行 schema 白名单校验。
- 校验 body 大小、Content-Type、同源/CSRF、字段长度和枚举。
- 以 `requestId + 标准化手机号 + 目标对象` 形成幂等键，并有数据库唯一约束。
- 使用共享限流，不以单进程内存作为生产唯一机制。
- 带房源时重新验证该房源当前有效；失效时不得创建指向无效房源的兴趣关系，可提示用户转为通用需求。
- 成功创建 Lead 时保存来源页面、目标对象、活动归因和隐私版本。
- 日志、分析和错误监控不得记录完整姓名、手机号或留言。

## 6. 错误与反馈

| 场景 | 用户反馈 |
|---|---|
| 字段错误 | 在字段附近显示中文错误并关联输入控件 |
| 房源刚失效 | 提示“该房源状态已变化，可提交通用选址需求” |
| 重复提交 | 返回与首次相同的成功语义 |
| 请求过多 | 提示稍后重试，不清空已填内容 |
| 网络失败 | 保留内容，允许用户重试 |
| 服务异常 | 中性提示和 request ID，不显示数据库或校验内部信息 |

## 7. 成功状态

- 明确表示已成功收到，而非承诺无法保证的固定回电时间。
- 提供关闭按钮。
- 可提供“继续浏览房源”或“返回当前页面”。
- 不展示内部 Lead ID 或负责人信息。

## 8. 埋点与隐私

- `inquiry_open`：入口和页面类型。
- `inquiry_submit`：字段完整度枚举，不含字段值。
- `inquiry_success`：目标类型、是否幂等命中。
- `inquiry_error`：安全错误码。
- 未勾选同意不得提交；隐私链接在不丢失表单内容的前提下可访问。

## 9. 验收标准

- 当必填字段合法且用户同意隐私政策时，系统应创建一条可归因的 Lead。
- 当同一请求因双击、刷新或网络重试重复到达时，系统应只创建一条 Lead。
- 当目标房源已失效时，系统不得继续建立有效兴趣关系，并应给用户可理解的替代路径。
- 当请求超过限额时，系统应返回 429 和合理重试提示，且不得记录完整 IP。
- 当用户使用键盘时，系统应正确锁定、循环和归还弹层焦点。
- 当发生校验或网络错误时，系统应保留用户已经填写的非敏感内容。
- 当查看日志、埋点和前端监控时，不应出现完整手机号、姓名或留言正文。

## 10. 非目标

- 短信验证码。
- 即时在线聊天。
- 自动分配顾问的前台展示。
- 用户账户和咨询历史。
