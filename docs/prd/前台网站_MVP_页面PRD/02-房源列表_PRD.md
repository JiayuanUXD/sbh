# FP-02 房源列表 PRD

> 路由：`/listings`  
> 优先级：P0  
> 状态：待确认

## 1. 页面目标

房源列表应帮助用户快速缩小候选范围、理解价格与位置差异，并稳定进入房源详情或咨询流程。

## 2. 用户故事

- 作为需求明确的用户，我希望组合区域、类型、面积和租金筛选。
- 作为比较多个方案的用户，我希望每张卡片的信息单位和层级一致。
- 作为移动端用户，我希望筛选不占据过多结果空间且条件可随时修改。

## 3. 筛选与 URL

### 3.1 基础筛选

- 关键词：房源标题、楼盘名称或地址的公开搜索能力。
- 城市、行政区、商圈。
- 办公类型。
- 面积最小值和最大值。
- 租金最小值和最大值；选择价格前必须明确单位。

### 3.2 更多筛选

- 地铁。
- 可入驻时间。
- 装修/配置或后台已定义的公开标签。
- 租赁/出售类型；不同类型不得使用同一价格解释。

### 3.3 URL 规则

- 所有有效筛选、排序和页码写入查询参数。
- 空值、默认值和非法值不进入 canonical。
- 修改任一筛选后页码回到 1。
- 浏览器前进、后退和刷新应复现页面状态。
- 数组参数规范排序，避免同一筛选产生多个 URL。

## 4. 结果区

- 展示规范化的结果总数和当前范围说明。
- 排序：推荐、最新、价格升序、价格降序。
- 默认每页 24 套。
- 桌面 3 列、平板 2 列、移动端 1 列。
- 分页必须稳定；相同查询重复访问不应因同权重数据顺序导致跨页重复。

### 4.1 房源卡片

- 封面、标题、楼盘、行政区/商圈。
- 面积、类型、可入驻时间（有值时）。
- 价格数值、币种、单位。
- 最多三个亮点。
- 完整卡片可点击，同时保留语义化链接。

### 4.2 移动端筛选

- 顶部保留结果数、排序与“筛选”按钮。
- 筛选使用底部抽屉或全屏面板。
- 用户点击“查看 N 套房源”后才应用暂存条件。
- 已应用条件以可删除标签显示。

## 5. 数据与业务规则

- 结果、总数、facet 和分页全部调用统一有效供给服务。
- facet 数量基于除当前 facet 自身外的已应用条件计算，并在实现任务中固定契约。
- 租金排序仅在可比较的币种和单位内生效；混合场景需先要求用户选择类型/单位或关闭该排序。
- 不为凑数量混入无效、跨城市或不匹配房源。

## 6. 页面状态

| 状态 | 表现 |
|---|---|
| 首次进入 | 默认推荐排序和默认城市 |
| 加载 | 保留页面框架，卡片骨架尺寸与实卡一致 |
| 无结果 | 展示已选条件、放宽建议、清除操作和提交需求 |
| 查询失败 | 显示重试，不把失败解释为 0 套 |
| 非法 URL | 安全规范化参数并生成正确 canonical |
| 页码越界 | 跳转最后有效页或规范化 404 策略，不显示空白页面 |

## 7. SEO、分析与可访问性

- 有业务价值的基础区域页可索引；高维组合默认 `noindex,follow`。
- 筛选区使用 `form`、可读 label 和分组语义。
- 结果数变化通过非打扰式 live region 通知。
- 事件：筛选修改、应用、清除、排序、翻页、卡片曝光和点击。

## 8. 验收标准

- 当用户组合筛选时，系统应返回全部且仅返回满足筛选和统一有效供给谓词的房源。
- 当用户刷新或分享 URL 时，系统应恢复相同筛选、排序和页码。
- 当有效供给条件改变时，结果、总数和 facet 应在同一失效窗口内同步更新。
- 当结果为空时，系统应保留用户条件并提供明确恢复路径，不展示不匹配房源。
- 当两条结果排序值相同时，系统应以不可变 `listing_id` 形成稳定次序。
- 当用户仅用键盘操作时，应可完成筛选、排序、翻页和进入详情。

## 9. 非目标

- 地图与列表联动。
- 收藏和登录同步。
- AI 自然语言找房。
- 跨币种实时换算。
