# 投放房源提交成功/失败交互设计

日期：2026-08-10
状态：已按用户审核意见确认，进入实施计划阶段
范围：前台 `/publish` 页面 `SupplySubmissionForm` 的提交反馈、重试、成功后动作与验收用例

## 背景

当前 `/publish` 页面已具备基础表单能力：

- 客户端字段校验：楼盘名称、详细地址、出租面积、手机号必填，租金可选但需为合法数值。
- 提交中状态：按钮显示 loading。
- 成功状态：表单卡片替换为“已收到您的房源”。
- 失败状态：字段错误映射到对应 Field，通用失败显示表单级错误文案。
- 幂等：同一次挂载内失败重试复用 requestId，同一意图在 sessionStorage 中复用 requestId。

2026-08-10 本地验证结论：

- 前端交互与请求体在拦截 API 成功响应时通过浏览器验证。
- 真实 API 合法提交在当前本地库返回 500，原因是本地数据库缺少 `supply_submissions` 表及相关迁移字段。这是本地数据库迁移问题，不应作为前端交互设计的阻塞，但真实提交验收必须在迁移完成后复测。

## 目标

1. 用户知道提交是否成功、失败原因属于哪一类，以及下一步该怎么做。
2. 失败后保留全部已填内容，并让用户可以明确重试。
3. 成功后给出明确返回路径，避免用户停在死胡同状态。
4. 对键盘和读屏用户可感知：状态变化可被读出，焦点有明确落点。
5. 不暴露手机号、楼盘名、详细地址等 PII 到日志、埋点或错误文案。

## 非目标

- 不改变 `/api/supply-submissions` 的业务规则、限流、幂等算法或数据库结构。
- 不新增多步骤向导，不拆分页面结构。
- 不引入 Toast、Modal 或全局通知系统。
- 不修改 `/entrust` 页面，除非后续单独批准同步体验。
- 不绕过或掩盖本地数据库迁移失败；真实 API 验收仍需数据库结构正确。

## 方案比较

### 方案 A：卡片内增强状态，推荐

保留当前单卡片表单结构，在表单顶部或提交按钮上方加入状态区。失败时显示用户能理解的错误提示和重试动作；成功时保留成功卡片，并提供返回首页动作。

优点：

- 改动面小，符合现有 `SupplySubmissionForm` 边界。
- 不引入全局状态或新组件系统。
- 易于用现有单测和 Playwright E2E 覆盖。
- 移动端不会产生浮层遮挡问题。

缺点：

- 成功后不保留原表单可见；用户若想连续投放，需要重新进入投放页。

### 方案 B：Toast + 表单内错误并行

通用失败用 Toast 提醒，同时保留字段级错误。

优点：

- 反馈更显眼。

缺点：

- 当前前台没有全局 Toast 体系，需要新增跨页面 UI 基础设施。
- Toast 对读屏、键盘焦点、移动端遮挡处理成本更高。
- 对这个单页表单收益不高。

### 方案 C：提交后进入独立结果页

成功或失败后跳到 `/publish/result`，展示结果和后续动作。

优点：

- 结果页可扩展更多运营内容。

缺点：

- 路由和状态传递复杂化。
- 失败后回填表单不自然。
- 当前业务只是轻量提交表单，跳转会增加用户成本。

推荐采用方案 A。

## 交互设计

### 初始状态

页面保持现有结构：

- 标题：`免费投放房源`
- 流程步骤：提交房源、实勘采集、推广曝光、签约成交
- 表单字段不变
- 提交按钮默认文案：`立即投放`

初始状态不展示错误区，避免增加视觉噪音。

### 客户端字段校验失败

触发条件：用户点击提交，客户端字段校验不通过。

行为：

- 不发送 API 请求。
- 保留全部已填内容。
- 对应字段下展示字段级错误。
- 将焦点移动到第一个错误字段。
- 表单顶部或按钮上方展示简短汇总：`还有几项信息需要补充，请检查后再提交。`
- 按钮文案保持 `立即投放`。

字段错误文案沿用现有文案：

- 楼盘名称：`请输入楼盘名称`
- 详细地址：`请输入详细地址`
- 出租面积空值：`请输入出租面积`
- 出租面积非法：`出租面积需为正数`
- 租金非法：`租金数值不合法`
- 手机号非法：`请输入正确的 11 位手机号`

### 提交中

触发条件：客户端校验通过，开始请求 `/api/supply-submissions`。

行为：

- 提交按钮 disabled，并显示 loading。
- 按钮可见文案建议为 `提交中...`。
- 表单字段保持可见，不清空。
- 不允许并发重复提交；继续复用现有 `pendingSubmission` 防重逻辑。
- 状态区可显示：`正在提交，我们会为您保留已填写的信息。`

### 服务端字段校验失败

触发条件：API 返回 422，且返回安全错误码。

行为：

- 保留全部已填内容。
- 将错误码映射到字段级错误。
- 将焦点移动到第一个错误字段。
- 状态区展示：`有几项信息还需要调整，请检查后再提交。`
- 按钮文案改为 `重新提交`。

说明：如果 422 返回了无法映射的错误码，不展示原始错误码，降级为通用失败文案。

### 限流失败

触发条件：API 返回 429。

行为：

- 保留全部已填内容。
- 状态区使用 `role="alert"` 展示：`刚才提交得有点频繁，请稍后再试。`
- 如果响应有 `Retry-After`，文案可显示为：`刚才提交得有点频繁，请约 1 分钟后再试。`
- 按钮文案改为 `稍后重试`，disabled 只在提交中生效，不做前端倒计时锁定。

### 网络异常

触发条件：`fetch` 抛错或浏览器离线。

行为：

- 保留全部已填内容。
- 状态区展示：`网络好像不太稳定，已填写的内容还在，请检查网络后再试。`
- 按钮文案改为 `重新提交`。
- 如果 `navigator.onLine === false`，文案可更明确：`当前网络不可用，已填写的内容还在，请恢复网络后再试。`

### 服务端异常

触发条件：API 返回 5xx 或不符合 `{ ok: true }` 的成功响应。

行为：

- 保留全部已填内容。
- 状态区展示：`暂时没有提交成功，已填写的内容还在，请稍后再试。`
- 按钮文案改为 `重新提交`。
- 不展示后端异常 message，不展示记录 ID，不展示内部错误码。

### 成功

触发条件：API 返回 200 且 JSON 为 `{ ok: true }`。

行为：

- 替换为成功卡片，保持当前页面 URL `/publish`。
- 成功卡片使用 `role="status"` 和 `aria-live="polite"`。
- 成功卡片容器设置可聚焦，提交成功后将焦点移动到成功卡片标题或容器。
- 成功标题沿用：`已收到您的房源`
- 成功说明沿用：`顾问将尽快与您联系，安排实勘与上架。`
- 增加一个主动作：`返回首页`，跳转 `/`。
- 不提供“继续投放另一套”。当前页面面向低频提交，成功后让用户回到首页更自然，也避免用户误以为需要重复提交。

## 状态模型

建议保持现有状态枚举：

- `idle`
- `submitting`
- `success`
- `error`

在 `error` 下增加安全的错误类型，用于按钮文案和状态区文案：

- `client_validation`
- `server_validation`
- `rate_limited`
- `network_error`
- `server_error`

字段错误继续使用 `fieldErrors`。

表单级错误继续使用 `formError`，但文案由错误类型统一生成，避免分散在多个分支里。

## 可访问性

必须满足：

- 字段错误通过现有 Field 关联到输入控件。
- 提交失败状态区使用 `role="alert"` 或 `aria-live="assertive"`。
- 提交中和成功状态使用 `aria-live="polite"`。
- 客户端和服务端字段校验失败后，焦点移动到第一个错误字段。
- 成功后焦点移动到成功卡片，读屏用户能听到成功标题。
- 按 Tab 可按视觉顺序经过所有输入、佣金选项、隐私政策链接和提交按钮。
- 375px 移动端无横向滚动，错误文案不撑破卡片。

## 埋点与隐私

继续沿用现有事件：

- `landing_form_submit`
- `landing_form_success`
- `landing_form_error`

允许新增安全枚举字段：

- `error_code`: `validation_failed`、`rate_limited`、`network_error`、`submit_failed`

禁止进入埋点：

- 手机号
- 楼盘名
- 详细地址
- requestId
- 后端异常 message

成功后的 `返回首页` 如需埋点，只允许记录：

- `page_type: "publish"`
- `action: "return_home"`

### 单元测试

更新或新增 `tests/supply-submission-form.test.ts`：

- 客户端字段错误保留值，并返回第一个错误字段标识。

更新 `tests/e2e/landing-pages.spec.ts` 或新增目标用例：

- 空提交：显示字段错误，焦点落到第一个错误字段，保留已填内容。

- API 429：显示限流提示，表单值保留。

- 四档视口：375×812、768×1024、1440×900、1920×1080 无横向滚动。
- 控制台无新增 error。
