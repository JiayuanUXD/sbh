这份 demo 在演示什么

  • 布局切换看首屏渲染量：Tab 条上的数字是该 tab 的输入数，🔥 表示含重组件。
  • 排列切换看省高。高度是离屏克隆实测——把同一份内容按 Payload 原样布局在等宽容器里重渲一遍再比，不是估算。
  • 租售切换看 admin.condition：出售时租期/付款/入驻日整行消失，出售信息组出现，发布必填清单跟着变。

五项优化（可逐项开关）

  • 去掉组框：结构化价格 / 空间明细 / 费用条款只留小标题。外框的内边距正是组内字段与组外 对不齐的原因，去掉后全表共用一条列轴。
  • 固定列轴：每节列数固定（基本信息 3 列、其余 4 列），行内字段不足时靠左留空而不拉满。 实测每行单元格都落在同样的 4 个左边界上、宽度一致。
  • 复选框对齐：网格里的复选框改成「标签在上 + 方框在控件行」。原来的 inline 写法没有标签行， 方框会浮到相邻输入框的中间高度。
  • 只读四项文本化并后置：不再是禁用输入框，说明收进 ⓘ；位置挪到供给商户 / 联系经纪人 / 核验信息之后——运营进这节是来填商户的，只读状态是「看一眼」的结论。字段顺序即显示顺序，不涉及 schema。
  • URL 标识收进标题框：不再占独立格子，做成标题输入框右侧的链接图标，hover 显示 /listings/xxx 与生成规则。比 admin.hidden 安全——隐藏字段仍在表单状态里 参与校验（fieldIsHiddenOrDisabled 只认顶层 hidden 和 admin.disabled）， 会被一个看不见的必填错误拦住保存；而顶层 hidden: true 会把 slug 从 API 响应里删掉，前台详情页直接崩。

为什么「展示内容」单独留一个 tab

  • Payload 3.86 客户端只渲染激活 tab（TabsFieldComponent 只给 activeTabConfig 渲一个 TabContent）。
  • 服务端 iterateFields 对 tabs 无条件全展开，所以通铺不增加服务端和 RSC 成本，只增加客户端 mount。
  • 媒体工作台（maxRows: 40）mount 即发 /api/media 请求并渲染最多 40 张缩略图；Lexical 富文本要实例化编辑器。把它们留在第二个 tab，通铺的收益全拿到、成本一点不付。
