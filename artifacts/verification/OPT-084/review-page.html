OPT-084 · 设计草案 · 2026-09-10

后台导航信息架构评审

现有导航是一份按数据模型分的集合目录：10 个一级分组、40 片叶子、最深 3 级， 把「让一套房源在前台可见」这一条业务流拆进 4 个分组。建议改成按工作流分的 8 组—— 待处理集中一处、供给链同组、层级压到 2 级、单叶分组自动扁平——菜单码与角色数据一个都不动。

结论 证据 现状树 → 目标树 问题清单 五角色视图 方案与分阶段 未决
结论

导航的形状忠实复刻了 31 个 collection 的领域切分，而不是运营每天要走的路。真实的日常在供给侧 （房源、楼盘、媒体、审核、导入、商户），这条链被切成了「房源运营 / 商户合作 / 区域管理 / 审核与风控」四段； CRM、举报、表单、待办这些模块在生产里还是空表，却各占一个一级位置。

推荐方案 B：按工作流重组为 8 组、≤ 2 级。所有「等我处理」的队列进「待处理」并在组头汇总角标； 房源 / 楼盘 / 商户 / 关系 / 导入同在「房源与楼盘」；解析后只剩一片叶子的分组自动扁平；消息通知挪到顶栏铃铛。

不动的东西
  • 每片叶子的 href、菜单码、操作码、collection access 原样保留
  • 不改 roles 表任何一条数据
  • 不删路由；退出导航的集合仍可直达
  • 不做按角色独立树、不做导航后台可配

03

问题清单

按影响排序，编号即优先级。

  1. 分组按数据对象而非工作流切分

    「房源上线」要在 楼盘库（房源运营）→ 楼盘商户关系（商户合作）→ 房源列表 → 审核队列（审核与风控）之间来回；有效供给 12 条谓词散在 4 个分组，排查「这套房源为什么前台看不到」没有一处能看全。OPT-045 实测：手工补 3 个楼盘商户关系约 18 次点击。

    结构

  2. 待处理的东西散在 5 个分组里，组头不显示角标

    7 个角标挂在 5 个分组的叶子上；分组默认折叠，折叠后角标不可见（只有叶子渲染角标）。角标的意义是把注意力拉过去，默认态却把它藏起来了。

    效率

  3. 广度过大，默认态信息量低

    ADM 10 组 40 叶，全部展开 999 px 高；默认只展开当前所在组，其余 9 个组头只是 9 个名字。生产 3 个用户全是 ADM，看到的正是这棵最重的树。

    结构

  4. 第三级只为一片叶子存在

    「系统管理 › 基础配置」下只有「配套字典」，e2e 把「只保留配套字典」写成了断言；OPS 为这一片叶子要进 3 级。

    结构

  5. 同一件工作两个入口、两种口径

    导航的「审核队列」指向 listing-reviews 自定义视图，运营概览的「待审核房源」指向 listings 的筛选；OPT-023 的角标事故就是这种双口径的症状。导入拆成 3 片叶子。

    一致性

  6. 两个仪表盘并列，职责边界不清

    「运营概览」（今日待办 + 供给健康度）与「数据看板」（趋势 / 分布 / 流量）指标重叠，用户不知道首页是哪一个。建议定位：概览管今天，看板管趋势。

    体验

  7. 个人收件箱混进全局树

    「消息通知」是「给我的」，却和「房源列表」同级；惯例是顶栏铃铛 + 未读数。

    体验

  8. 空模块占一级位置

    表单中心、客户运营、团队管理、城市合伙人申请在生产里都还没开始用，却与「房源运营」平级。不是删功能，而是它们不该在当前阶段占首屏。

    效率

  9. 命名不一致、组叶重名、工程词汇外露

    「团队管理 › 团队管理」相邻出现；「提交数据」不知所指；「导入批次 / 搜索索引 / 领域事件」是工程概念；「顾问服务时间」是前台预约带看时段的配置却挂在团队下。

    命名

  10. 单叶分组没有兜底

    菜单码按对象授予，角色被裁剪后常剩「一个组头 + 一片叶子」（BRK 的房源运营、OPS 的系统管理）；解析器没有扁平化规则。

    规则

  11. 找一条具体记录没有快捷路径

    Cmd/Ctrl+K 只搜地理数据；2.2k 房源、83 楼盘的日常是「找到那一套」。导航层管不了，但目标 IA 要给它留位置（Phase 3）。

    效率

05

方案与分阶段

A 微调作为 B 的第一阶段吸收；C 按角色独立树不做——5 棵树要维护，生产只有 3 个 ADM。

Phase 1 · 约 1 天

纯配置 + 渲染规则

改 navigation-config / types / resolver / client；不动权限
  • 按目标树重排；删子分组类型
  • 单叶分组扁平化（服务端解析器）
  • 组头汇总角标；收起态图标带数
  • 默认展开「待处理」+「房源与楼盘」，用户开合记忆
  • 新增 投放申请 / 信息纠错 两条角标查询
  • 重写树快照、e2e 角色矩阵、geography-admin 断言
Phase 2 · 约 1 天

两个小组件

铃铛 + 一物一入口 + 导入三合一
  • 顶栏通知铃铛，未读数沿用现有角标查询
  • 概览待办卡片 href 复用导航配置
  • BulkImportView 加模式切换与「导入记录」tab
  • 命名收口：叶子标签 = 集合 labels.plural = 页面 h1
Phase 3 · 待裁定

依赖别的裁定

先看 Phase 1 上线后的反馈
  • 「领域事件」退出导航（绑定 OPT-043）
  • Cmd/Ctrl+K 扩到房源 / 楼盘 / 商户
  • 空模块的阶段性可见性，不预先建机制

未决，需裁定

  • Q1
    「顾问服务时段」归「团队与账号」还是「站点与内容」？
    建议前者：MGR 视图保持完整；它本质是前台预约带看的时段表，两种归法都说得通。
  • Q2
    「领域事件」是否退出导航？
    绑定 OPT-043 的删 / 接 / 拆裁定；退出只是不进树，路由仍在。
  • Q3
    「数据看板」与「概览」长期并存，还是并成概览的一个 tab？
    建议并存：概览管今天，看板管趋势。
  • Q4
    命名收口与结构重组同批上，还是拆成第二个 PR？
    改名要连 collection labels.plural 一起改，否则 e2e 的 h1 断言会红；建议拆开，先动结构。
  • Q5
    批量导入三合一进 Phase 1 还是 Phase 2？
    要动 BulkImportView 路由，建议 Phase 2；Phase 1 先把三片叶子放进「房源与楼盘」并把「导入批次」改名「导入记录」。
