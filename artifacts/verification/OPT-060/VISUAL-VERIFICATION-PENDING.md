# OPT-060 视觉验证：待补清单

**这份文件列的是目前完全没有证据支撑的结论。** 本轮验收拿到的是配置生效证明
（后台实配后前台 `<img src>` 确实变成配的那张图）、DOM 结构、`getComputedStyle()`
在给定视口宽度下的真实布局计算结果、真实 HTTP 响应内容——这些证明的是
「数据被正确传到了决定渲染结果的属性/接口上」，**不证明肉眼看到的画面是对的**。
比如 `getComputedStyle` 读到 `display:none` 只说明这条 CSS 规则确实命中了，
不说明：图片区域收起后旁边的文字/编号有没有跟着重新对齐、有没有残留色块；
`<img src>` 指向配置的那张图，不说明这张图配上卡片的裁切比例（`ratio="auto"`
+ 容器固定高度）之后，主体有没有被裁掉关键部分、观感是否整洁。**这不是
「差最后一层薄薄的确认」，这是视觉验收本来要验的东西**，本次都没验到。

## 待补的四张截图

### 1. `types-desktop.png` —— 首页「按类型浏览」区块，桌面视口

- **访问**：桌面浏览器窗口（不缩放，1440px 或更宽），打开 `/shanghai`
  （多城市路由已开启；根路径 `/` 会重定向到目标城市，重定向没生效就直接访问
  `/shanghai`）。
- **看什么**：`.hm-types` 里五张类型卡（传统办公 / 联合办公 / 整层办公 /
  独栋办公 / 创意园区）的封面图——图片有没有被拉伸变形（长宽比不对、
  建筑物看起来被压扁或拉长）；卡片编号（`01`–`05`）、类型名文字、
  在租套数是否都在图片之上正确叠放，没有被图片盖住或错位。
- **看到什么算通过**：每张有图的卡片都是「铺满容器、按比例裁切、无变形
  拉伸、主体清晰」；文字与编号清晰可读、不被图片遮挡。看到任何一张图
  明显压扁/拉长，或文字被图片盖住，都算不通过，记下是哪张卡、什么问题。

### 2. `types-mobile.png` —— 「按类型浏览」区块，375px 窄屏

- **访问**：开发者工具切到设备模拟（或直接把窗口缩到 375px 宽），刷新
  `/shanghai`。
- **看什么**：`step7-breakpoints-computed-style.txt` 里已经证明
  ≤767px 时 `.hm-type-card__media img` 的 `display` 计算值是 `none`——
  这份待补截图要确认的是**图片收起之后卡片的实际观感**：每一行是否变成
  横向紧凑行（左侧编号 + 右侧文字），编号列区域里有没有任何残留的色块/
  方形占位；五行之间的间距、对齐是否整齐一致。
- **看到什么算通过**：五行紧凑、干净，只有编号+文字，没有色块或空白
  占位；行与行之间对齐整齐。看到编号列有灰色/彩色方块，或行高不一致，
  算不通过。

### 3. `district-bento-desktop.png` —— 「热门商圈」bento 区块，桌面视口，含精选拉升的商圈

  远宽于高）这个特殊比例下，构图好不好看完全没有人看过。
- **访问**：`/shanghai`（如果本轮验证时的「大宁」测试数据已被还原，参照
  README「数据清理」一节的做法，临时把某个现有商圈加入
  `CitySiteProfiles.featuredRegions` 第一位即可复现同样的场景，验完照
  同样方式还原）。
- **看什么**：bento 区块大卡（1 张）、竖排小卡（2 张，232px 高）、底行
  宽卡（2 张，280px 高）——三种尺寸各自的封面图裁切构图是否合理，主体
  （楼盘外立面、天际线等）有没有被裁掉关键部分；大卡与小卡、宽卡叠放的
  文字标签（商圈名、在营楼盘名）是否清晰、没有和背景图的高对比度区域

### 4. `district-bento-mobile.png` —— 「热门商圈」bento 区块，375px 窄屏

- **访问**：同上，浏览器切到 375px 宽，刷新首页。
- **看什么**：bento 五张卡应该纵向堆叠成一列，`step7-breakpoints-computed-style.txt`
  已证明三种卡在这个断点下统一为 232px 高——待确认的是堆叠后**卡与卡之间
  有没有视觉层叠、溢出或多余留白**，以及高度看起来是否真的一致（不只是
  计算值一致，肉眼观感也要一致，字号/内边距在窄屏下有没有把内容挤出卡片）。
- **看到什么算通过**：五张卡纵向排列、间距均匀、高度肉眼看起来整齐；
  没有内容溢出卡片边界或互相压盖。看到层叠/溢出/高度明显不一致，算不通过。

## 为什么本次没做到

本会话的 Browser pane 全程处于「未显示，不合成帧」状态，截图类调用
会报类似：

```
Screenshot timed out after 5s: the Browser pane is not displayed, so the page is not compositing frames. Display the pane and retry.
```

这是**会话级限制**（与 `artifacts/verification/OPT-059/VISUAL-VERIFICATION-PENDING.md`
记录的同一根因），不是被测功能的问题：浏览器压根没有产出任何一帧画面，
所以拿不到像素级证据。本轮改用 `javascript_tool`/DOM API 在真实运行的
浏览器标签页里驱动真实的表单保存、拿到真实的 HTTP 响应与真实布局计算结果
（`getComputedStyle`），这些证据是可信的，但天然不能替代「肉眼看画面」这一步。

## 补做步骤（写给没有本次会话上下文的人）

1. 确认在分支 `feat/opt-060-homepage-cover-config-3b8e`（或它已合并到的分支）上。
2. `cd payload-office-platform && pnpm exec payload migrate` —— 确保本地库
   迁移是最新的，否则可能看到「缺列导致 500」这类跟本次改动无关的假象。
3. 起 dev server：Claude Code 环境下用 `preview_start`；本地终端直接跑
   `pnpm dev`（固定端口 3717，多 worktree 并行时换 `PORT`，别跟其它会话
   抢同一个端口——这是本仓库已记录的坑，见 `payload-office-platform/CLAUDE.md`
   「并行开发纪律」）。
4. 打开一个**真正显示在屏幕上**的浏览器窗口/面板（这正是本次会话缺的
   那一环），访问 `http://localhost:3717/admin/login`，用
   `scripts/seed.ts` 里的 E2E 夹具账号登录（如 `e2e-adm@example.com`，
   密码写在该文件里，是公开夹具不是真凭据）。
5. 按上面「1. `types-desktop.png`」「2. `types-mobile.png`」直接访问
   `/shanghai` 截图即可，不需要额外造数据（现有 seed 数据已经有类型卡
   与商圈封面）。
6. 按「3. `district-bento-desktop.png`」的准备步骤，进入后台
   「内容管理 → 城市站点配置」，编辑上海（或任一已开城的城市），把某个
   现有商圈加进「精选区域」第一位，保存后访问 `/shanghai` 截图；验完把
   「精选区域」这一行删掉，保存还原。
7. 把浏览器切到 375px 宽（设备模拟或直接缩窗口），刷新 `/shanghai`，
   按「2」「4」分别截 `types-mobile.png` 与 `district-bento-mobile.png`。
8. 把四张图放进 `artifacts/verification/OPT-060/`，按上面「看到什么算
   通过」逐条核对，把结论（通过/不通过 + 具体问题）补进 `README.md`。
