## 2. 已修复阻断级问题

### B7（已修复）：限流键使用原始 IP，违反注释声明的 hashIpForLog

**位置**：`payload-office-platform/src/app/api/inquiries/route.ts`

**问题**：注释声明「限流键使用 hashIpForLog(ip, dailySalt) 派生，避免原始 IP 进入内存或日志」，实际代码 `checkRateLimit(rateStore, ip, ...)` 直接用原始 IP 作 key。`hashIpForLog` 是死代码，从未被调用。`rateStore: Map<string, ...>` 内存里保留着用户原始 IP。

**修复**：
- `route.ts:106` 改为 `const rateKey = hashIpForLog(ip, getDailySalt())`
- 新增 `getDailySalt()` 返回 UTC 日期字符串（YYYY-MM-DD），跨天自动轮换
- `privacy-log.ts:15` 改为静态 `import { createHash } from 'node:crypto'`，删除 `require()` 写法
- `idempotency.ts:21` 同步改为静态 import
- 测试 `__resetRateStoreForTests()` 在 `beforeEach` 中调用，避免用例间状态污染

**验证**：1787 个测试全部通过；hashIpForLog 现在被 route.ts 实际调用。

## 3. 已修复非阻断问题

### N1（已修复）：JSON-LD `dangerouslySetInnerHTML` 存储型 XSS

**位置**：
- `payload-office-platform/src/app/(frontend)/listings/[slug]/page.tsx:123-131`
- `payload-office-platform/src/app/(frontend)/buildings/[slug]/page.tsx:116-122`
- `payload-office-platform/src/app/(frontend)/pages/[slug]/page.tsx:92-98`

**问题**：`JSON.stringify(jsonLd)` 不转义 `</script>` 子串。若管理员在 CMS 字段（标题/摘要）中存入 `</script><script>alert(1)</script>`，浏览器会闭合当前 script 标签并执行注入代码。利用前提是具备后台编辑权限。

**修复**：三处统一改为 `JSON.stringify(jsonLd).replace(/</g, '\\u003c')`。

## 4. 通过审查项

### 4.1 公开 DTO 字段白名单 — 通过

`src/domain/public-catalog/`：
- `contracts.ts` DTO 类型采用显式字段白名单，未声明 `merchant / contactBroker / reviewStatus / publicationStatus / supplyVisibilityHold / version / internalNotes / rejectionReason` 等内部字段
- `mappers.ts` 严格按字段白名单投影：`mapListingCard` / `mapListingDetail` / `mapBuildingDetail` / `mapPageDetail` 未读取内部字段
- `facade.ts:112-117` 的 `lastEffectiveMaintainedAtOf` 读取原始 `updatedAt` 仅用于内存排序，不写入 DTO

### 4.2 PageContent 白名单渲染器 — 通过

`src/components/frontend/PageContent.tsx`：
- 文件头注释明确「不使用 dangerouslySetInnerHTML，所有节点都通过 React 元素渲染」
- 节点类型白名单：`paragraph / heading / quote / list / upload / horizontalrule / text / link / linebreak / tab`
- 外链渲染加 `rel="noopener noreferrer nofollow"`
- 未支持节点 `console.warn` 跳过，不渲染 `script / iframe / object / embed`

### 4.3 /api/inquiries 路由安全 — 通过

- 仅接受 POST + application/json + 同源
- body 上限 16KB
- schema 白名单收窄 unknown → InquiryRequest
- 幂等键 sha256(requestId + normalizedPhone + targetType + targetSlug) + DB 唯一约束兜底
- 限流 5 次/分钟/IP（哈希后）+ Retry-After
- 失效房源 → 409 listing_not_found，不建 Lead
- 响应固定 `{ ok: true } | { ok: false, errors } | { ok: false, error }`，不暴露 Lead ID
- 4 个 `payload.logger.info` 调用均走 `buildInquiryLogEntry`
- 日志含 `phoneMasked / fieldCompleteness / campaignKeys`，不含 `name / phone 原值 / message / 原始 URL / IP`

### 4.4 /api/dictionaries 鉴权 — 通过

`src/endpoints/dictionaries-endpoint.ts:40-46` 调用 `requireAdminContext`，未登录返回 401。

### 4.5 sitemap — 通过

- 房源通过 `adapter.findEffectiveListings` 走完整有效供给谓词，草稿/驳回不进 sitemap
- 楼盘 `where: { status: 'published', ...buildingOperationalWhere() }`
- 内容页 `status=published` + `deletedAt exists false`
- 不含 `/dev-story`、`/api/`、`/admin` 路径
- 跳过 `/pages/home` 避免与 `/` 重复

### 4.6 分析事件 — 通过

`InquiryModal.tsx` 的 8 处 `trackEvent` 仅记录枚举与上下文：
- `page_type` / `target_type` / `field_completeness` / `error_code` / `idempotent` / `has_target`
- 未记录任何字段值（name / phone / company / message / demand.* 均未进入 trackEvent）
- 生产环境仅 push 到 `window.dataLayer`；非生产环境 `console.debug`

### 4.7 CSRF / 同源校验 — 可接受

- 现代浏览器跨源 POST + application/json 触发 CORS 预检，带 Origin，校验生效
- 同源 POST 可能省略 Origin，缺 Origin 时放行，依赖 Content-Type + consent.policyVersion + 幂等 + 限流二层防护
- 对浏览器 CSRF 已有效

## 5. 阻断级问题（待后端任务修复）

> 以下问题涉及后端 Collection access 策略与 Payload REST/GraphQL 默认端点暴露，
> 属于 M1 权限收窄范畴，不属 F7.5 修复范围。记录在此作为发布前阻断清单。

### B1：Leads 集合缺少 access.read，公开可读 PII

**位置**：`src/collections/Leads.ts`（无 `access` 字段）

**影响**：客户姓名、公司、留言正文（notes）、sourceUrl、UTM 参数、idempotencyKey 等通过 `/api/leads` 或 GraphQL 任意查询。`phone` 字段被 `afterRead` 脱敏，但其余 PII 全部明文。

**修复方向**：增加 `access.read` 要求 `lead:read` 权限；前台 `route.ts` 已用 `overrideAccess: true` 不受影响。

### B2：Merchants 集合 `access.read: () => true`，泄露商户联系人手机号

**位置**：`src/collections/Merchants.ts:74-76`；`contactName` / `contactPhone` 字段（行 104-115）

**影响**：商户联系人姓名与明文手机号对外公开。无 afterRead 脱敏。

**修复方向**：增加 `access.read` 要求 `merchant:read` 权限；运营/管理员不受影响。

### B3：ListingReviews 集合公开可读，泄露审核驳回原因与快照

**位置**：`src/collections/ListingReviews.ts:40-45`；`reason` / `snapshot` / `snapshotHash` 字段

**影响**：内部审核理由、提交快照（房源字段 JSON）对外公开。

**修复方向**：增加 `access.read` 要求 `review:read` 权限。

### B4：Listings 集合公开可读，泄露草稿/驳回房源与内部状态轴

**位置**：`src/collections/Listings.ts:34-36`；`reviewStatus / publicationStatus / supplyVisibilityHold / version / merchant / contactBroker` 字段

**影响**：绕过 Facade 有效供给谓词，草稿与未发布房源可通过 `/api/listings` 直查；depth≥1 时连带泄露商户 contactPhone。

**修复方向**：
- 方案 A：增加 `access.read` 要求 `listing:read` 权限；前台 Facade + sitemap + cached-queries 改用 `overrideAccess: true`
- 方案 B：保留 `read: () => true`，但在 `afterRead` hook 中按 `req.user` 脱敏内部字段（与 Buildings 一致）
- 推荐 A（更彻底，避免绕过路径）

### B5：Buildings 集合公开可读，泄露草稿楼盘与运营字段

**位置**：`src/collections/Buildings.ts:57-59`；`status / operationalStatus / verificationStatus / recommendedOrder / version` 字段
注：`latitude / longitude` 已被 afterRead 脱敏（Buildings.ts:64）。

**影响**：草稿、下架、停用楼盘可被直查（坐标已脱敏，是唯一做了字段级保护的集合）。

**修复方向**：同 B4。

### B6：GraphQL 端点无查询白名单

**位置**：`src/app/(payload)/api/graphql/route.ts`；`payload.config.ts` 未配置 `disableGraphQL` 或白名单

**影响**：B1-B5 的字段可通过 GraphQL 任意选择查询，攻击面比 REST 更精细。

**修复方向**：
- 评估 C 端是否依赖 GraphQL（当前不依赖）→ 直接 `disableGraphQL: true`
- 或保留但启用查询白名单 / Persisted Query
