- **方法**：全部为**匿名只读 GET / GraphQL 查询**，未做任何写操作、未登录、未修改任何数据。逐集合探测 + 关系展开绕过测试 + `where` 参数枚举测试 + GraphQL 权限对照。

## 一句话结论

**16 个集合 + 2 个 Global 对匿名用户完全可读**，其中最实的一条是 `/api/listings` 可用 `where` 参数**精确枚举出 42 条未发布（draft / not_submitted）房源并读到完整字段**。但没有发现任何**已锁集合被绕过**的路径——权限模型本身是成立的，问题在于哪些集合被划进了「公开」这一侧。

更关键的判断：**这些集合的匿名可读对公开站点没有任何功能价值**。C 端走 Local API（默认 `overrideAccess: true`），不经过 REST 权限；浏览器端只打 `/api/corrections` 与 `/api/inquiries` 两个专用端点。唯一的真实依赖是 **Media**（图片经 `/api/media/file/...` 提供，受集合 read 权限管辖）。

## 二、可实际利用的路径（唯一一条，但很实）

```
GET /api/listings?limit=0&where[publicationStatus][equals]=draft   → totalDocs = 42
GET /api/listings?limit=0&where[reviewStatus][equals]=not_submitted → totalDocs = 42
```

去掉 `limit=0` 即可读到这 42 条的**全部 37 个字段**，实测包含 `title` / `area` / `rent` / `price` / `description`（富文本正文）。

含义：**尚未上架、尚未提审的房源，它的定价、面积、描述对任何人可读**。对商办租赁而言，未发布的报价被竞对或客户提前拿到，是可以直接影响谈判的。

## 三、同样重要的负面结论（这些**没有**被绕过）

逐条测过，都成立：

| 测试 | 结果 |
|---|---|
| 关系展开绕过：`/api/brokers?depth=3` 能否展开受限的 `users` | ❌ 不能。`broker.user` 始终返回 id 整数，Payload 在填充关系时会重新校验目标集合权限 |
| GraphQL 是否是另一条口子 | ❌ 不是。`{ Users }` `{ Leads }` 均 403，`{ Listings }` 可读——与 REST 完全同一套权限 |
| GraphQL introspection | ✅ 已关闭（`GraphQL introspection is not allowed`） |
| 软删房源是否泄露 | ✅ 未泄露，抽样 300 条 `deletedAt` 全为 null |
| 询价 / 供给提交端点 | ✅ 405，只收 POST |
| 后台用户表 | ✅ 403 |

也就是说：**权限模型本身是对的，实现也没漏**。问题纯粹在「哪些集合被划到了公开这一侧」。

## 四、影响判断：这是设计意图，还是意外？

`Listings.access.read` 上有一条明确注释：

> 「前台匿名可读——公开站点靠有效供给谓词在查询层收窄，不靠 access.read」

所以**放开这件事是刻意的**，不是有人随手写的。没被考虑到的是它的副作用：`read: () => true` 同时打开了 Payload 自带的 REST + GraphQL 端点，而那两条路**不经过「有效供给谓词」**——注释里承诺的收窄只发生在 C 端查询层，攻击者直接打 `/api/listings` 就绕过了整个前提。

而实际上，**C 端根本不需要这个放开**：

- C 端 Server Component 用 `getPayload()` + `payload.find()`（Local API），Local API 默认 `overrideAccess: true`，压根不走 access 检查。仓库里显式传 `overrideAccess: false` 的只有后台看板统计（`domain/analytics/dashboard-stats.ts`），是刻意的。
- 浏览器端只有两个 fetch：`/api/corrections`（信息纠错）和 `/api/inquiries`（询价留电），都是专用端点，与集合 REST 权限无关。

**唯一的真实依赖是 Media**：图片经 `/api/media/file/...` 提供，该路由受 `Media.access.read` 管辖。把 Media 锁成登录可读，访客会看不到任何图片。处理 Media 需要单独设计（例如只放开文件路由、收紧文档列表），不能和其它集合一刀切。

## 五、可选的处置方向（未执行，等你定）

按「改动面 / 风险」从小到大：

1. **只堵最实的那条**：给 `listings` 的 read 加上「未发布不可读」的谓词（把 C 端注释里承诺的收窄真正下沉到 access 层）。改动最小，直接消掉 42 条草稿的暴露。
2. **收紧 CRM 那组**：`follow-ups` `lead-ownership-history` `teams` 改成登录可读。当前为空，**改动零风险、零回归**，纯粹是拆掉地雷。
3. **收紧内部关系与商户**：`merchants` `brokers` `building-merchant-relations` 改成登录可读。需要先确认 C 端有没有哪个页面通过 Local API 之外的路径读它们（我看到的都是 Local API，但值得再核一遍）。
4. **全面翻转默认**：除 Media 与确实要公开的内容集合（`articles` `pages` `locations` `amenities` `city-site-profiles` `buildings` `listings`）外，其余一律登录可读。最彻底，但要逐个跑一遍 C 端回归。
5. **Media 单独设计**：文件路由保持公开、集合文档列表收紧，避免 17048 条媒体元数据可被整表拉取。

无论选哪条，都要注意：**改 access 属于 collection 配置变更**，按仓库约定要带迁移、并且合并到 master 会直接上线。建议单开分支 + 真实回归（C 端全站 + 后台）。

## 六、与「房源详情加房间号」的关系

这正是这份清单的起因。结论：

- 直接加一个普通字段 → 它会出现在 `/api/listings` 的匿名响应里，**「只有后台可见」不成立**。
- 对口的机制是**字段级 access**：`access: { read: ({ req }) => Boolean(req.user) }`，匿名请求会把该字段整条剥掉；C 端 Local API 仍读得到（但前台是显式 DTO 映射，不加就不渲染）。
- 仓库目前**没有字段级 access 的先例**（`.agent/permissions.md:27` 提过「手机…按字段权限脱敏」的原则，但未落地），所以这会是第一处，值得把写法定成范式。
