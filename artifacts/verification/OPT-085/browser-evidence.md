## 1. 两套列表 UI 并存（硬证据）

同一个后台里有两种完全不同的列表实现，视觉、控件、能力、分页默认值都不一样。

| 页面 | 实现 | `.arco-table` | `.table table`（原生） | 批量选择 | 每页默认 | 筛选形态 | 行内操作列 |
|---|---|---|---|---|---|---|---|
| 房源列表 | Arco 自定义 | ✅ | ❌ | **无** | 25 | 顶部 4 个下拉 + 搜索框 | 编辑 / 前台 |
| 楼盘库 | Arco 自定义 | ✅ | ❌ | **无** | 25 | 顶部 4 个下拉 + 搜索框 | 编辑 / 前台 |
| 城市管理 | Arco 自定义 | ✅ | ❌ | 无 | — | 状态下拉 + 搜索 | 编辑 |
| 审计日志 | Arco 自定义 | ✅ | ❌ | 无 | — | 动作 / 结果两个下拉 | 详情 |
| 审核队列 | Arco 自定义视图 | ✅ | ❌ | 无 | — | 无（固定 pending） | 行内动作 |
| 用户管理 | Payload 原生 | ❌ | ✅ | **有** | **10** | 「列」+「过滤条件」弹层 | 无 |
| 咨询线索 | Payload 原生 | ❌ | ✅ | 有 | 10 | 同上 | 无 |
| 商户管理 | Payload 原生 | ❌ | ✅ | 有 | 25 | 同上 | 无 |
| 我的待办 | Payload 原生 | ❌ | ✅ | 有 | 10 | 同上 | 无 |
| 房源投放申请 | Payload 原生 | ❌ | ✅ | 有 | 10 | 同上 | 无 |
| 素材库 | 插件卡片网格 | — | — | 有（批量上传） | **10** | 「过滤条件」+ 网格/列表切换 | 无 |

两个直接后果：

- **最大的两张表反而不能批量操作。** 2 229 条房源、83 个楼盘走 Arco 视图，没有复选框；而 3 条商户、5 个用户走原生表，有全套批量选择。批量能力和数据量成反比。
- **同一件事两种手势。** 想加一列，在房源列表做不到，在用户管理点「列」；想按字段筛，在房源列表用顶部下拉，在用户管理点「过滤条件」开弹层。分页默认值 10 / 25 混用。

## 2. 角色权限编辑是裸 JSON 代码编辑器

`/admin/collections/roles/2`（运营人员 OPS）实测：菜单权限、操作权限、字段权限三个字段全部渲染成带行号的 JSON 代码块，运营要手写字符串数组。

```
菜单权限
 1 [
 2     "dashboard",
 3     "todos",
...
19     "form-submissions"
菜单权限可多选；* 表示全部菜单。
```

字段说明写着「可多选」，但界面上没有任何可多选的控件。OPS 当前是 19 个菜单码 + 20 个操作码 + 3 个字段码，共 42 行 JSON 分三块手写。拼错一个码有 `validate` 拦（`Roles.ts:141` 起），但拼对却给错人、或漏给一个码，没有任何提示。「四层权限」这个设计的可用性完全卡在这里。

## 3. 房源编辑页：「审核与发布」区里既不能审核也不能发布

`/admin/collections/listings/1` 实测结构：

- 2 个 tab：房源信息 / 展示内容
- 主区 8 个分节：基本信息 → 价格与交易参数 → 空间明细 → 费用条款 → **审核与发布** → 核验信息 → 状态（只读）→ 数据来源
- 38 个字段标签，主区滚动高度 **2 326 px**（视口 1000 px，约 2.3 屏）
- 顶部两张自定义卡片：「信息完整度 100%」「前台可见性：自身条件已齐」（4 个勾：已上架 / 审核通过 / 可见性正常 / 未被举报暂停）
- **文档控件区只有一个按钮：保存**

「审核与发布」这个分节里只有「供给商户」「联系经纪人」两个关系字段，以及紧随其后的「状态（只读）」。分节名承诺的两个动作，在这个页面上一个都做不了——审核要去审核台，发布要去别处。

「前台可见性」卡片自己写明：**「仅校验房源自身条件；商户 / 楼盘 / 服务城市等关联条件未包含在内」**。也就是说这套房源在前台到底可不可见，这张卡答不了，运营还要自己去另外三个分组核对。

对照楼盘编辑页 `/admin/collections/buildings/1`：5 个 tab（基本信息 / 位置交通 / 楼宇属性 / 媒体与配套 / 介绍与 SEO），主区 1 494 px，文档控件区有**两个**按钮：停用、保存。同为供给主数据，一个有状态动作按钮，一个没有。

## 4. 线索表单 7 个 tab，创建页第一屏只有 6 个字段

`/admin/collections/leads/create` 的 tab：客户信息 / 租赁需求 / 归属与阶段 / 结构化需求 / SLA 与快照 / 跟进记录 / 前台询盘上下文。

第一个 tab 只有 6 个字段（姓名、联系电话、公司、跟进状态、线索来源、负责经纪人）。新建一条线索要在 7 个 tab 里找该填哪个，而实际必填只有前两个。「租赁需求」与「结构化需求」两个 tab 名相近，从标签看不出分工。

## 5. 待办与投放申请：原生列表给了不该有的「创建新条目」

- 我的待办 `/admin/collections/tasks`：页面说明写着「**由来源业务事件驱动创建与闭环**」，页面右上却有「创建新条目」，空态还引导「创建新的 待办」。手工建的待办没有来源事件，不会闭环。
- 房源投放申请 `/admin/collections/supply-submissions`：说明写着「业主/物业/中介从 /publish 提交房源投放申请，提交零文不可改」。这是纯外部写入对象，后台侧不存在「新建一条投放申请」这件事。

## 6. 审计日志：查看审计本身被审计，且淹没真实操作

`/admin/collections/audit-logs` 共 62 条，**最新一条是「审计日志详情已查看」**（2026/09/10 12:14:10，对象 `audit-logs / 61`）。每点一次详情就多一条，按时间倒序排在最前，真实业务操作（「房源由管理员直发上架」）被顶下去。

另外两列可读性问题：「操作人」显示的是数字主键 `1` 而不是人名；「请求 ID」整列全是 `—`。

## 8. 站点设置：水印参数整组重复

`/admin/globals/site-settings` 6 个 tab（品牌 / 合规声明 / 页脚 / 首页区块 / 导航 / 图片水印）。「图片水印」tab 内主区高 1 501 px，里面「详情大图（满铺）」与「卡片缩略图（角标）」两组各自重复同一套参数：水印源、文案、角度、透明度、字号。两组之间没有「继承 / 覆盖」关系，改一处不影响另一处。

## 9. 地理城市管理是唯一一个「带指标的列表」

`/admin/geography/cities` 每行 8 个数值列：行政区数 / 商圈数 / 缺边界商圈 / 地铁线路数 / 站点数 / 楼盘数 + 状态 + 前台可见。上海一行是 16 / 29 / 29 / 23 / 399 / 7。

这是全后台唯一一处把「数据完备度」直接做进列表的页面，方向是对的。但「缺边界商圈 29」与「商圈数 29」相等（全部缺边界）却没有任何视觉告警，纯文本数字；「前台可见」列显示「是 / 否」文本而不是状态标记。

## 10. 批量导入落地页结构良好

`/admin/import/listings`：说明 → 两个模板下载按钮（房源导入模板 / 楼盘对照表）→ 本批默认值三个下拉（供给商户 / 房源类型 / 装修）→ 「选择文件并开始预检」。预检不写库、需人工确认才导入，这条流程在全后台里是设计得最完整的一个。

问题只在导航层：它被拆成「楼盘批量导入」「房源批量导入」「导入批次」三个入口（见 OPT-084）。

> **口径订正（同日补）**：本节的 2 326 px 是 `.document-fields__main` 的 `scrollHeight`，含顶部两卡与 tab 条；该页面已由 OPT-032 第三部分重排并合并（PR #68），其 1 735 px 目标是离屏克隆的表单高度，两者口径不同，不能据此判断 OPT-032 未达标。见 OPT-085 §7.1、OPT-086 §3。
