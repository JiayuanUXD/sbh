# MP-103 微信开发工具链安全评估

> 评估日期：2026-08-27
> 结论：保持阻断，不降低全量审计门槛，不通过传递依赖 override 制造“假绿”。

## 1. 当前证据

- `pnpm audit --audit-level high`：3 low、25 moderate、27 high、7 critical。
- `pnpm audit --prod --audit-level high`：0 个已知漏洞。该结果只证明小程序运行产物没有生产依赖漏洞，不替代开发工具链审计。
- 风险来自三个直接开发依赖：
  - `miniprogram-ci@2.1.31`
  - `miniprogram-automator@0.12.1`
  - `miniprogram-simulate@1.6.2`
- 2026-08-27 查询 npm registry：三者当前 `latest` 分别仍为 `2.1.31`、`0.12.1`、`1.6.2`，与仓库锁定版本一致。
- `miniprogram-ci` 存在 `gamma@2.1.38`、`alpha@2.1.42`、`beta@2.1.46`，但其依赖清单仍包含 `babel-core@6.26.0`、`html-minifier@4.0.0`、`download@8.0.0`、`minimatch@3.0.4`、`protobufjs@6.x`、`tmp@0.0.28` 等已命中漏洞的旧链路，不能把预发布升级视为安全修复。

## 2. 为什么不直接 override

审计中既有可升级的叶子依赖，也有当前没有修复版本的依赖，例如旧 `babel-traverse`、`html-minifier`、`decompress` 和 `image-size` 链路。跨主版本 override 会改变微信工具的解析、构建、图片和归档行为；在没有官方兼容声明和真实预览/上传回归的情况下，强行替换只能改变审计数字，不能证明工具安全或可用。

## 3. 当前风险边界

- 这些包不进入小程序运行包，生产依赖审计为零。
- 风险仍然真实存在于开发机和 CI：它们会解析项目输入、图片、CSS、归档，启动本机开发者工具，或在显式预览时访问微信服务。
- `ci:preview` 不是安装、测试或普通 CI 的隐式步骤；本轮未执行 preview、upload 或 deploy。
- `devtools:smoke` 仅在操作者显式提供本机 CLI 后运行；失败路径另有进程级有界退出回归，不用人工 `Ctrl-C` 作为正常流程。

## 4. 推荐处置

1. MP-103 保持“代码完成，依赖安全处置与微信环境验收待完成”，Task 7 的全量审计步骤不勾选。
2. 当前小程序 CI 只运行安装、单元测试、类型检查和工程合同，尚未纳入 audit；在依赖处置方案确定前，全量审计继续作为手工阻断门，生产依赖审计必须保持零 high/critical。后续若把 audit 纳入 CI，不能通过忽略退出码或只跑 `--prod` 冒充全量门通过。
3. 在官方包发布可清除 high/critical 的稳定版前，不在持有正式上传私钥的通用 CI 环境执行微信工具链；预览使用单独、最小权限、短生命周期的受控环境。
4. 只处理受信任仓库内容，不让外部提交、任意图片/CSS/归档直接触发上述工具；正式私钥只在明确授权的预览任务中临时注入。
5. 官方版本更新后重新执行：全量审计、工具脚本测试、开发者工具双页冒烟、预览二维码生成与清理测试。全部通过后才解除阻断。

## 5. 未作出的决定

本评估没有接受安全例外，也没有把全量门禁改成仅审计生产依赖。若业务需要在官方修复前发布，必须另行明确接受有时限、可撤销、带补偿控制的工具链例外；不能由自动化测试结果代替该决定。
