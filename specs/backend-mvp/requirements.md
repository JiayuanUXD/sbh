# 商办租赁后台 MVP — 需求基线

## 1. 问题与目标

当前 Payload 后台已具备楼盘、房源、线索、区域、媒体和基础工作台，但尚未形成 PRD 要求的“可信供给 + 线索跟进 + 权限审计”闭环。

本期目标：

1. 房源能够独立完成资料维护、送审、审核、显式发布、下架和出租。
2. 线索能够完成去重、分配、认领、跟进、转派、公海回收和阶段流转。
3. 商户、经纪人、团队和区域主数据能够约束供给与线索归属。
4. 五类内置角色按照菜单、操作、数据和字段四层权限访问后台。
5. 工作台、看板和操作日志使用统一业务口径，可下钻、可追溯。

## 3. 用户故事

### US-1 平台管理员

作为平台管理员，我需要维护账号、角色、区域和字典，并查看全局日志，以保证系统权限、基础数据和关键操作可控。

### US-2 运营人员

作为运营人员，我需要维护楼盘和房源、处理审核与举报，并控制房源发布，以保证前台供给真实、完整和可追溯。

### US-3 销售主管

作为销售主管，我需要管理团队、分配或转派线索并查看团队进展，以保证客户得到及时承接。

### US-4 经纪人

作为经纪人，我需要查看本人客户、记录跟进、推荐有效房源和安排下次跟进，以持续推进客户阶段。

### US-5 客服

作为客服，我需要创建、补充和查重线索，并将未分配需求交给销售团队，以减少重复客户和信息缺失。

## 4. 功能需求与验收条件

### R1 统一身份与权限

- 当用户访问后台菜单、调用业务操作或读取敏感字段时，系统应同时校验菜单权限、操作权限、数据范围和字段权限。
- 当账号被停用时，系统应阻止登录并撤销全部有效会话。
- 系统应固定保留 `ADM / OPS / MGR / BRK / CSR` 五种内置角色，不允许删除或改变其内置身份。
- 当用户没有完整手机号权限时，列表、详情和导出应返回脱敏值。

### R2 地理、商户与组织主数据

- 当管理员维护城市、行政区、商圈、地铁线路或站点时，系统应校验固定层级、不可变编码、父级状态和引用保护。
- 当区域节点停用时，系统应禁止新增业务引用，同时保留历史对象展示。
- 当商户、经纪人或团队被停用且仍有有效业务关联时，系统应阻止直接停用或要求完成影响确认、转派或供给冻结。
- 当 Building 或 Listing 建立商户关系时，系统应保存有效期关系并禁止同一对象出现重叠有效区间。

### R3 楼盘管理

- 当运营人员创建或编辑楼盘时，系统应校验城市、区域、商圈、地址、楼盘等级和同城重复楼盘。
- 当楼盘资料完整且状态启用时，系统应允许房源选择该楼盘。
- 当楼盘停用时，系统应撤销其前台有效性，但不得隐式改写关联房源的审核状态或发布状态。
- 当用户预览楼盘时，系统应展示已保存楼盘内容及符合统一有效供给谓词的房源聚合。

### R4 房源审核与发布

- 当创建房源时，系统应分别初始化 `publication_status=草稿`、`review_status=未提交` 和 `supply_visibility_hold=正常`。
- 当用户提交审核时，系统应验证完整字段和至少 3 张有效图片，创建不可变审核快照，并仅将审核状态改为待审核。
- 当审核人通过或驳回时，系统应保存审核记录；驳回必须填写原因。
- 当审核通过时，系统不得默认上架；只有具备发布权限的用户完成显式发布后，发布状态才能变为已上架。
- 当房源标记已出租时，系统应将发布状态改为已出租并撤销推荐。
- 前台、预览、楼盘聚合和看板应复用同一有效供给谓词。

### R5 举报处理

- 当举报进入系统时，系统应支持分诊、领取、核实、等待资料、提交复核、恢复展示或关闭。
- 当举报导致供给暂停时，系统应暂停房源前台可见性，但保留审核和发布状态。
- 当举报处理进入负向结论时，系统应要求原因、保存证据与不可变处理记录。

### R6 客户、线索和跟进

- 当录入手机号时，系统应按规范化手机号查询客户历史，并按 30 天窗口判断重复线索。
- 当线索创建时，系统应进入新建或待分配状态，并保存来源和 `MVP-R1` 运行参数快照。
- 当有权限用户分配、认领或转派线索时，系统应校验城市、团队、人员状态、每日认领上限和活跃线索上限。
- 当线索分配或认领成功时，系统应从成功事件时刻计算 4 小时首次有效跟进期限。
- 当经纪人提交跟进时，系统应保存不可物理删除的历史记录，并更新最后跟进和下一次跟进时间。
- 当跟进结果为已推荐时，系统应要求至少关联一套当前有效房源。
- 当线索满足公海回收规则时，系统应按 72 小时无有效跟进口径回收，并保存归属变更历史。

### R7 工作台与数据看板

- 当用户进入工作台时，系统应按角色和数据范围展示待办、SLA、供给和线索指标。
- 当点击指标卡时，系统应使用同一指标编码和查询上下文下钻到明细。
- 当来源业务处理完成、取消或失效时，系统应在 60 秒内同步完成或取消对应待办。
- 当单个指标加载失败时，系统应保留其他指标并提供局部重试。
- 所有“今日”和时间范围统计应按北京时间计算。

### R8 审计、通知与可靠性

- 当发生新增、编辑、审核、发布、下架、分配、转派、导入导出、权限或敏感字段读取时，系统应写入结构化审计日志。
- 审计日志应追加写入、不可由后台修改或删除，并保存请求 ID、操作者与权限快照、对象版本、结果和脱敏前后值。
- 当高风险操作无法写入审计日志时，系统应阻止业务操作成功。
- 当用户提交旧版本对象时，系统应阻止覆盖并提示刷新。
- 批量操作应限制批量规模、二次确认，并返回逐条成功或失败原因。

## 5. 约束

- 技术栈保持 Payload CMS 3.86、Next.js 16、React 19 和现有数据库适配器。
- 数据关系使用不可变内部 ID，不以名称、手机号或展示文案作为业务主键。
- 状态机使用固定机器字段；字典配置不得改变审核、发布、线索阶段等核心状态。
- SQLite 用于本地开发；生产 PostgreSQL 的关系有效期重叠约束需要数据库级保障。
- 使用逻辑删除或停用保护有关联的数据；审核、跟进和审计记录不可物理删除。

## 6. 非目标

- 在线支付、佣金、财务、发票。
- 合同、成交报备和完整带看闭环。
- 电话外呼、录音和深度 IM。
- 自动派单策略引擎、智能推荐和复杂风控。
- 完整商户开放平台和复杂 CMS 专题搭建器。
