**版本：** V0.9

**状态：** 需求评审稿  
**阶段：** Spec Workflow / Phase 1 Requirements  
**适用对象：** 产品、设计、前端、后端、测试、运营、销售

## 1. 项目背景

平台后台已经规划楼盘、房源、区域、商户、经纪人、审核、发布、线索和审计能力，但前台仍需要一套与后台数据口径一致、面向企业选址用户的产品需求基线。

前台 MVP 的核心不是复制综合房产信息平台，也不是建设在线交易平台，而是：

1. 帮助企业用户快速缩小办公空间选择范围。
2. 用可信、结构化的楼盘和房源信息降低决策成本。
3. 通过低摩擦咨询入口形成可追踪线索。
4. 将“高端服务感”与“高效率找房”结合，而不是只展示房源卡片。
5. 确保前台、后台预览、楼盘聚合和数据看板对同一房源的可见性结论一致。

## 2. 竞品研究摘要

本 PRD 仅提炼产品能力，不复制竞品的品牌、页面文案、图片、视觉设计、广告位或专有内容。

### 2.1 58 商办

参考页面：[上海 58 商办](https://shangban.58.com/sh/)

可借鉴能力：

- 以城市、行政区、商圈、类型、面积、价格和人数为核心的快速筛选。
- 同时覆盖传统写字楼、联合办公等不同办公需求。
- 列表直接展示区域、价格、面积、可租数量和关键标签。
- 在首页、列表和详情保持明显的咨询入口。
- 通过“业主直租、专业顾问、海量楼盘”等信任信息降低留资阻力。

明确不采用：

- 竞价广告、置顶推广、经纪人广告体系。
- 住宅或其他房产业务混合导航。
- 在线交易、支付、担保或佣金能力。
- 未经后台可信供给校验的信息直接展示。

### 2.2 德事商务中心

参考页面：[德事商务中心官网](https://www.executivecentre.com.cn/)、[上海共享办公室](https://www.executivecentre.com.cn/locations/shanghai/coworking-spaces-in-shanghai/)

可借鉴能力：

- 以空间品质、企业形象、服务体验和地标位置建立高端信任。
- 按私人办公室、共享办公、日租办公室等使用场景解释产品。
- 使用真实空间大图、空间体验和设施服务，而不是只罗列参数。
- 城市与区域落地页兼顾用户决策和搜索引擎收录。
- 咨询、参观和方案定制贯穿页面，但不打断主要阅读。

明确不采用：

- 会员、通行证、会议室在线预订和全球中心网络。
- 虚拟办公室、行政秘书、活动场地等当前后台不支持的业务。
- 将单一品牌自营空间的叙事直接套用到多楼盘平台。

### 2.3 搜楼网 soolou

参考页面：[搜楼网](https://www.soolou.com/)、[上海楼盘列表](https://www.soolou.com/sh/loupan?quyu=164&shangquan=194)、[楼盘详情示例](https://www.soolou.com/sh/loupanshow/4180)

可借鉴能力：

- 楼盘列表展示可租面积范围、可租套数、区域地址和最低租金。
- 楼盘详情提供在租面积、平均或最低租金、楼宇参数、物业、网络和介绍。
- 楼盘与具体房源分层，适合从楼盘概况继续查看可租单元。
- 通过区域、商圈和楼盘详情形成可索引的信息网络。

明确不采用：

- 缺少后台有效供给验证的数据聚合。
- 仅为 SEO 堆叠的重复页面和重复文案。
- 电话号码抓取、未经用户同意的营销触达。

### 2.4 差异化定位

平台前台采用：

> 58 商办的找房效率 + 搜楼的楼盘数据深度 + 德事的品质与服务表达。

差异化约束：

- 所有可见房源必须来自统一有效供给查询。
- 楼盘聚合值只能由当前有效房源计算，不允许人工填写虚假最低价或套数。
- 咨询线索必须携带明确页面、楼盘、房源和筛选来源。
- 不承诺“最低价”“真实率 100%”“免佣”等无法被后台证据支持的内容。

## 3. 产品目标与指标

### 3.1 MVP 目标

- 用户能够在 3 分钟内从首页进入筛选结果并找到至少一个匹配房源。
- 用户能够理解楼盘与具体可租单元的区别。
- 用户能够在任意核心页面提交一次结构化咨询。
- 销售团队能够识别线索来源、意向房源和原始筛选条件。
- 无效、冻结、未审核或已下架房源不得通过任何前台入口访问。

### 3.2 北极星指标

`有效咨询线索数`

有效咨询定义：

- 手机号格式合法并完成服务端规范化。
- 用户主动同意隐私条款。
- 来源页面和来源渠道可追踪。
- 非接口限流、机器人或重复提交产生的无效记录。

### 3.3 辅助指标

| 指标 | 定义 |
|---|---|
| 搜索到详情率 | 从首页或列表发起搜索后进入房源/楼盘详情的会话数 ÷ 有搜索行为的会话数 |
| 详情咨询率 | 在房源或楼盘详情提交有效咨询的会话数 ÷ 详情会话数 |
| 筛选使用率 | 使用至少一个区域、面积、价格或类型筛选的会话数 ÷ 列表会话数 |
| 有结果搜索率 | 返回至少一个有效房源的搜索次数 ÷ 全部搜索次数 |
| 咨询完成率 | 成功创建线索次数 ÷ 打开咨询表单次数 |
| 无效供给曝光数 | 前台曝光后被证明不满足统一有效供给谓词的房源数，目标为 0 |

所有指标按北京时间统计，并保存统一 query ID、筛选上下文和数据截至时间。

## 4. 目标用户与核心场景

### U1 企业决策者

关注企业形象、地段、总成本、面积、注册能力、交通和交付时间，希望快速获得少量高质量选项。

### U2 行政或选址负责人

需要比较多个区域和楼盘，关注面积、工位、装修、租金单位、配套、可用日期和通勤。

### U3 创业团队负责人

预算敏感，倾向服务式办公室或联合办公，希望按照人数、月租和是否可立即入驻筛选。

### U4 异地或跨城企业

对本地市场不熟悉，需要城市、区域、商圈、地铁和专业顾问解释。

### U5 搜索引擎访客

从具体楼盘、区域或办公类型关键词进入，需要快速确认页面与需求是否匹配，并继续查询或咨询。

## 5. MVP 信息架构

```text
首页 /
├── 找办公室 /listings
│   ├── 筛选结果
│   └── 房源详情 /listings/[slug]
├── 楼盘详情 /buildings/[slug]
├── 类型入口
│   ├── 传统办公 /listings?type=traditional-office
│   ├── 服务式办公 /listings?type=serviced-office
│   ├── 共享办公 /listings?type=coworking
│   └── 整层办公 /listings?type=full-floor
├── 城市/区域落地
│   └── 通过可索引筛选 URL 或后续独立落地页承载
├── 内容页 /[page-slug]
│   ├── 服务说明
│   ├── 隐私政策
│   └── 关于平台
└── 全局咨询入口
```

MVP 核心页面：

1. 首页。
2. 房源搜索与列表。
3. 房源详情。
4. 楼盘详情。
5. 全局咨询表单。
6. 后台 Pages 驱动的基础内容页。

## 6. 统一体验与视觉方向

本节是需求阶段的设计方向提案，需在进入 `design.md` 前确认。

### DESIGN SPECIFICATION

1. **Purpose Statement**  
   面向正在做重要办公选址决策的企业用户，界面需要同时传达可信数据、专业判断与空间品质。用户应快速完成筛选，又能在详情页感受到办公空间对企业形象和工作体验的价值。

2. **Aesthetic Direction**  
   `Editorial / magazine` 与 `Luxury / refined` 的克制组合。首页和详情偏空间杂志式叙事，搜索列表偏高效率的专业工具，不采用住宅房产平台的拥挤广告感。

3. **Color Palette**

   - 墨黑 `#171A1D`：主文字、导航和高端基调。
   - 暖象牙白 `#F5F1E8`：页面主背景。
   - 建筑灰 `#D5D0C7`：边框、分隔和次级背景。
   - 铜金 `#A46F3F`：重点价格、品质标签和关键装饰。
   - 深青绿 `#1F5A50`：主要行动按钮、有效状态和交互焦点。

4. **Typography**

   - 中文展示标题：`Source Han Serif SC`。
   - 中文正文与数据：`Source Han Sans SC`。
   - 英文及数字辅助：`IBM Plex Sans`。
   - 字体使用本地或合规 CDN 子集，避免阻塞首屏。

5. **Layout Strategy**  
   首页采用非对称 12 栏编辑式布局，让搜索模块与主空间图形成错位叠合；详情页采用大图叙事区与粘性决策侧栏；列表页采用紧凑筛选工具区和留有呼吸感的横向房源卡片。移动端重排为单列，不保留只适合桌面的视觉错位。

### 6.1 通用交互规则

- 所有按钮使用统一专业图标库，不使用 emoji 作为功能图标。
- 桌面端导航保持稳定，移动端使用可访问菜单。
- 价格、面积和数量优先使用等宽数字。
- 咨询按钮不得遮挡房源信息或浏览器系统手势区域。
- 页面必须包含加载、空结果、请求失败、已失效和无权限/不可访问状态。
- Light 为 MVP 默认主题；前台 MVP 不要求 Dark Mode。
- 所有核心功能满足键盘操作、可见焦点、语义标签和基本 WCAG 2.1 AA 对比度。

## 7. 功能需求与验收条件

### R1 全局导航与城市上下文

#### 需求

- 全局导航包含品牌入口、找办公室、办公类型入口、服务说明和咨询入口。
- 当前城市在导航和搜索区明确展示。
- MVP 可先以单城市运营，但路由、数据查询和 SEO 结构不得把上海写死为不可扩展常量。
- 页脚包含服务范围、联系方式、隐私政策、备案信息和风险声明。

#### EARS 验收

- 当用户点击品牌标识时，系统应返回当前城市首页。
- 当用户切换城市时，系统应清空不属于新城市的区域、商圈和地铁筛选。
- 当某城市未开放服务时，系统应展示可理解的未开放状态，而不是返回空白页面。
- 当页面展示联系电话时，系统应使用后台批准的公共联系方式，不得暴露房源内部联系人手机号。

### R2 首页

#### 页面目标

在一个首屏内回答“在哪里、需要多大、预算多少、要什么类型”，并建立平台专业可信的第一印象。

#### 页面结构

1. 主视觉与核心价值表达。
2. 快速找房表单。
3. 精选有效房源。
4. 热门区域或商圈。
5. 办公类型场景解释。
6. 服务流程与平台可信信息。
7. 顾问咨询行动区。
8. 基础内容/市场洞察入口。

#### 快速找房字段

- 城市。
- 行政区/商圈。
- 办公类型。
- 面积或团队人数。
- 预算口径。

面积与人数只能作为两种输入方式，不得在没有明确换算规则时自动互相改写。

#### EARS 验收

- 当用户提交快速找房时，系统应跳转到 `/listings` 并在 URL 中保留所有合法筛选值。
- 当精选房源加载时，系统应仅返回当前有效供给，且使用后台推荐权重和稳定次序。
- 当某推荐房源在缓存期间失效时，系统应在进入详情前再次校验并停止展示。
- 当首页局部模块加载失败时，系统应保留其他模块并为失败模块提供重试。
- 当首页没有精选房源时，系统应展示找房咨询行动，不得伪造推荐数据。

### R3 房源搜索与列表

#### 查询与筛选

MVP 支持：

- 城市、行政区、商圈。
- 地铁线路或地铁站。
- 办公类型。
- 面积区间。
- 租赁单价区间或总月租区间。
- 装修。
- 可注册。
- 直租。
- 可用日期。
- 关键词：楼盘名称、地址或商圈。

租赁单价和总月租必须分开筛选；币种、单位和周期必须明确。MVP 不允许跨币种排序或比较。

#### 结果卡片

展示：

- 真实封面图及图片数量。
- 房源标题。
- 楼盘名称。
- 行政区、商圈、地址摘要和最近地铁。
- 面积、可容纳工位。
- 租赁单价和总月租。
- 办公类型、装修、可注册、直租、认证等有证据支持的标签。
- 可用日期。
- 查看详情和咨询操作。

#### 排序

- 默认推荐。
- 最近维护。
- 面积从小到大/从大到小。
- 同口径租赁单价。
- 同币种总月租。

#### EARS 验收

- 当用户改变筛选条件时，系统应更新 URL、结果数量和列表，并保留可分享、可刷新恢复的状态。
- 当用户同时选择冲突价格口径时，系统应要求保留一种口径，不得混合比较。
- 当筛选下限大于上限时，系统应阻止查询并定位错误字段。
- 当用户返回列表时，系统应恢复原筛选、排序、页码和滚动位置。
- 当结果为空时，系统应保留筛选条件，提供调整建议和携带当前需求的咨询入口。
- 当 Listing、Building、区域或商户不满足统一有效供给谓词时，系统不得在结果、数量或筛选聚合中包含该房源。
- 当分页发生数据变化时，系统应使用稳定排序避免同一房源在相邻页重复出现。

### R4 房源详情

#### 页面目标

帮助用户判断一个具体办公单元是否满足面积、预算、交付、位置和企业形象要求，并形成咨询。

#### 页面结构

1. 图片画廊。
2. 标题、楼盘、位置和可信标签。
3. 面积、价格、工位、楼层、装修和可用日期。
4. 粘性咨询侧栏。
5. 房源亮点与详细说明。
6. 所属楼盘摘要。
7. 地图和交通。
8. 同楼盘其他有效房源。
9. 相似有效房源。
10. 风险声明与举报入口。

#### 业务规则

- 价格必须展示币种、数值、单位和周期。
- 日租单价可以同时展示后台已持久化的月租总价，但页面不得自行用浮点数重新计算业务权威值。
- 联系人手机号默认不直接公开；点击咨询创建线索，由后台路由给有效顾问。
- “可注册、认证、直租”仅在后台固定字段和证据有效时展示。

#### EARS 验收

- 当用户直接访问有效房源 URL 时，系统应展示当前发布版本，而不是后台工作草稿。
- 当房源已失效或从未有效发布时，系统应返回 404/410 语义页面，且不得泄露标题、价格、联系人或审核状态。
- 当用户打开图片画廊时，系统应支持键盘、触控、关闭和图片替代文本。
- 当用户点击所属楼盘时，系统应进入对应楼盘详情。
- 当展示同楼盘或相似房源时，系统应再次应用统一有效供给谓词。
- 当用户从房源详情提交咨询时，系统应保存 `listing_id`、`building_id`、页面 URL、来源渠道和提交时筛选上下文。

### R5 楼盘详情

#### 页面目标

以楼盘为稳定主对象，展示位置、楼宇品质、配套和当前有效供给聚合，支持用户在同一楼盘内比较具体房源。

#### 页面结构

1. 楼盘图集与名称。
2. 区域、商圈、地址和交通。
3. 当前有效租金范围、面积范围和可租套数。
4. 楼盘等级、竣工时间、楼层、电梯、物业、停车和注册能力。
5. 楼盘介绍与特色。
6. 地图与周边 POI。
7. 当前有效房源列表及二次筛选。
8. 顾问咨询入口。

#### EARS 验收

- 当楼盘存在有效房源时，系统应按 Listing 去重计算可租套数、面积范围和同口径价格范围。
- 当楼盘没有有效房源但楼盘允许保留 SEO 页面时，系统应明确显示“暂无可租房源”，不得展示历史最低价或历史套数，并提供需求登记。
- 当楼盘或所属区域停用时，系统应停止公开访问楼盘详情。
- 当房源商户变化时，系统不得把 Listing 商户信息反写为楼盘固有属性。
- 当楼盘展示认证、可注册、直租或直售标签时，系统应遵循后台 PRD 中 Building 自有字段与 Listing 聚合字段的边界。

### R6 全局咨询与线索创建

#### 入口

- 首页快速咨询。
- 搜索结果卡片。
- 房源详情。
- 楼盘详情。
- 空结果页面。
- 页脚或移动端固定咨询入口。

#### 表单字段

- 姓名：必填。
- 手机号：必填。
- 公司：可选。
- 意向城市：自动带入，可编辑。
- 意向区域：自动带入，可选。
- 面积、预算、计划入驻时间：按入口带入，可补充。
- 意向房源/楼盘：系统带入，不由用户输入内部 ID。
- 留言：可选。
- 隐私政策同意：必选。

#### 业务规则

- 手机号先规范化，再按后台客户历史和 30 天重复线索窗口处理。
- 客户端不得决定是否合并客户或覆盖旧线索。
- 重复提交、限流和线索去重必须在服务端处理。
- 浏览器不得直接获得 Payload 管理 API 凭证。
- 来源必须区分首页、列表、房源详情、楼盘详情、自然搜索和活动参数。

#### EARS 验收

- 当用户提交合法表单时，系统应只创建一次线索并返回明确成功状态。
- 当手机号格式非法或未同意隐私政策时，系统应阻止提交并在对应字段解释原因。
- 当相同请求因网络重试再次到达时，系统应通过幂等键避免重复创建。
- 当命中重复线索规则时，系统应按后台规则处理并向用户返回中性结果，不泄露已有客户或线索信息。
- 当请求超过限流阈值时，系统应返回可理解提示并记录安全事件。
- 当提交失败时，系统应保留用户已填非敏感内容并允许重试。

### R7 内容页与 SEO

#### 需求

- 首页、列表、房源详情、楼盘详情和基础内容页具有唯一 title、description 和 canonical。
- 楼盘、区域和办公类型形成可理解的内部链接。
- sitemap 仅包含当前允许索引的公开页面。
- 已失效房源从 sitemap 移除。
- 筛选组合默认不全部索引，避免无限参数页面和重复内容。
- 结构化数据必须与页面可见信息一致，不得标记不存在的价格、评分或库存。

#### EARS 验收

- 当房源有效发布时，系统应允许其进入 sitemap，并在失效后按刷新策略移除。
- 当筛选 URL 不属于允许索引模板时，系统应设置 canonical 或 noindex。
- 当内容页发布状态不是已发布时，系统应禁止公开访问和索引。
- 当生成结构化数据时，系统应使用当前公开字段并通过基本 schema 校验。
- 当页面分享时，Open Graph 图片不得使用无权公开或已删除媒体。

### R8 性能、响应式与可访问性

#### 性能目标

- 移动端核心页面 LCP 目标不高于 2.5 秒（P75，真实用户监测口径）。
- CLS 目标不高于 0.1。
- INP 目标不高于 200ms。
- 首屏图片按设备尺寸优化，非首屏媒体懒加载。
- 搜索筛选不因每次按键触发无节制请求。

#### EARS 验收

- 当用户使用 360px 宽移动设备时，核心筛选、价格、图片和咨询操作应完整可用且无横向页面滚动。
- 当用户使用键盘操作时，导航、筛选、画廊、弹窗和提交均应可达且焦点顺序合理。
- 当用户开启减少动态效果时，系统应关闭非必要位移动画。
- 当图片加载失败时，系统应保持布局稳定并提供符合内容的替代状态。
- 当 JavaScript 延迟加载时，首屏可索引内容和主要页面结构仍应由服务端输出。

### R9 数据一致性与缓存

#### 统一有效供给谓词

前台所有查询必须复用后台基线定义的同一服务端谓词：

- Listing 未逻辑删除。
- `publication_status=已上架`。
- `review_status=审核通过`。
- `supply_visibility_hold=正常`。
- 未被有效举报暂停。
- 媒体完整。
- Building、城市和区域启用。
- 当前 Listing 商户关系有效。
- 商户启用、资质通过且未过期。
- 商户启用的服务城市覆盖 Building 所属城市。

#### EARS 验收

- 当任一有效供给条件失效时，系统应在缓存失效策略内从首页、列表、详情、楼盘聚合、相关推荐和 sitemap 同时撤销该房源。
- 当后台仅修改草稿工作版本时，系统应继续展示已批准的当前发布版本，不得泄露草稿。
- 当价格、面积或媒体发布版本变化时，系统应使相关列表、详情和楼盘聚合缓存一致失效。
- 当同一 query ID 用于结果数量和明细列表时，两者应应用完全相同的筛选与权限口径。

### R10 隐私、安全与合规

#### 需求

- 咨询表单明确展示隐私政策并取得主动同意。
- 手机号、姓名和公司信息不得写入 URL、前端日志、分析事件明文或搜索引擎页面。
- 所有表单执行服务端校验、限流、CSRF/来源校验和机器人防护。
- 第三方地图、分析和客服脚本必须在清单中登记，并遵守同意策略。
- 页面不得公开内部 ID、审核状态、商户资质快照、后台备注和审计信息。

#### EARS 验收

- 当用户未同意隐私政策时，系统应阻止创建线索。
- 当分析事件记录咨询行为时，系统应仅记录匿名会话 ID、来源和对象内部追踪键，不得记录手机号和姓名。
- 当接口收到前端伪造的负责人、团队或线索状态时，系统应忽略这些字段并由服务端生成。
- 当公开 API 请求未授权字段时，系统应不返回字段，而不是仅通过 CSS 隐藏。

## 8. 页面公共状态

所有核心页面必须定义：

- 首次加载。
- 局部加载。
- 正常数据。
- 空数据。
- 筛选无结果。
- 请求失败及重试。
- 页面或对象已失效。
- 网络断开。
- 表单提交中、成功、字段失败、服务失败和重复提交。

不得用虚假房源、虚假最低价或静态成功提示掩盖服务异常。

## 9. 数据对象边界

| 前台对象 | 后台来源 | 前台约束 |
|---|---|---|
| 楼盘 | Building | 稳定主数据；不等同具体可租单元 |
| 房源 | Listing 当前发布版本 | 必须满足统一有效供给谓词 |
| 区域/商圈/地铁 | Locations | 只展示启用节点；历史关联不得进入新筛选候选 |
| 价格 | Listing 结构化金额字段 | 数值、币种、单位和周期一起展示 |
| 楼盘聚合 | 有效 Listing 实时/缓存聚合 | 不在 Building 持久化套数和最低价 |
| 顾问 | Broker/服务端路由 | 不直接公开内部手机号和归属规则 |
| 咨询 | Lead/Customer | 服务端查重、归属和 SLA；前端不决定阶段 |
| 内容页 | Pages | 仅已发布内容公开 |

## 14. MVP 总体验收

### 正常流程

- 用户从首页选择区域、面积和预算，进入对应列表。
- 列表数量、卡片和详情均来自相同有效供给查询。
- 用户进入房源详情、查看楼盘与图片并成功提交咨询。
- 后台线索保存来源、房源、楼盘和筛选上下文。

### 数据正确性

- 构造已上架但未审核、审核通过但未上架、待复核、举报暂停、区域停用、商户过期和媒体不足房源，前台所有入口均不得展示。
- 楼盘可租套数、面积范围和价格范围与有效 Listing 去重聚合一致。
- 日租单价、月租总价、币种和单位不混算。

### 异常流程

- 对失效详情 URL 返回不泄露内部信息的 404/410 页面。
- 搜索失败保留筛选并可重试。
- 咨询重复提交不产生重复线索。
- 图片、地图或局部推荐失败不阻断核心详情和咨询。

### 响应式与可访问性

- 桌面、平板和 360px 移动端完成首页搜索、筛选、详情和咨询。
- 键盘完成导航、筛选、画廊关闭和表单提交。
- 主要文字和操作达到 WCAG 2.1 AA 对比度。
