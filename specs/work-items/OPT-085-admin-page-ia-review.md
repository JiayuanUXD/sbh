## 1. 先回答第一问：之前没有梳理过

OPT-084 把 31 个 collection、2 个 Global、9 个自定义视图**作为导航输入**清点了一遍，但没有逐页看信息结构与交互。本项补这一层。

## 2. 一句话结论

后台的**数据层与规则层做得很扎实，动作层大面积缺席**：至少 7 个业务对象写了完整状态机、权限码和领域服务，UI 上却没有任何按钮能推进它们——运营看得见状态，够不着开关。房源举报与信息纠错是极端案例：状态字段 `readOnly`，说明写着「由状态转换服务推导」，而那个服务的 endpoint **根本不存在**，两条业务线在后台走 UI **完全无法处理**。

## 4. 横向模式：七个跨页面反复出现的问题

逐页问题的清单在 §5，但真正值得先解决的是这七个模式——它们各自横跨 5 个以上页面，单页修补只会修出七种不同的补丁。

### M1 有状态机，无操纵杆（最严重）

写了状态机、权限码、领域服务，UI 上却没有按钮能推进。

| 对象 | 状态机 | UI 上的动作 | 判据 |
|---|---|---|---|
| 房源举报 | 6 态（`report-status.ts:22`） | **无**。`status` 是 `readOnly`，说明写「由状态转换服务推导，不接受外部直接指定」（`ListingReports.ts:271`），而 `transitionReportStatus`（`report-transition.ts:88`）**零生产调用点**，`src/endpoints/` 下无 listing-reports 端点 | 已核实 |
| 信息纠错 | 4 态 | **无**。`status` 同为 `readOnly`（`InformationCorrections.ts:180`），无 endpoint。状态永远停在 `new`，与字段说明「由后台流转」自相矛盾 | 已核实 |
| 线索阶段 | 8 态 + 转换表 + `requiresLossReason` | 普通 select，可任意跳选。`canTransitionStage`（`lead-stage.ts:65`）**零生产调用点**；**`lossReason` 字段根本不存在** | 已核实 |
| 线索归属 | 分配/转派/认领/公海/回收，纯逻辑齐全（`domain/crm/ownership.ts`） | **无 endpoint、无 UI**。唯一路径是去归属历史表手工新建一条，而那张表已被排除出导航 | 已核实 |
| 待办 | 5 个 endpoint（`my-tasks-endpoint.ts:27`：mine/claim/transfer/batch-claim/batch-transfer） | **组件里零调用**。且 `createTaskFromEvent` 因 OPT-043 零调用，表长期为空 | 已核实 |
| 通知 | 已读 | 勾 checkbox 再点保存。无「标记已读」「全部已读」，来源 ID 不可点 | 已核实 |
| 房源发布 | publish / unpublish / mark_leased（`listing-publish-endpoint.ts`） | 只有 `publish` 有一个半入口（审核台的「通过后上架」）。**`unpublish` 与 `mark_leased` 全后台 `.tsx` 零引用**——运营在后台无法下架一套房源 | 已核实 |

**唯二做对的**：房源审核台（通过/驳回/撤回 + 乐观锁 + 确认抽屉 + 缺失项预警）和楼盘停用（先查影响面 `GET /:id/deactivation-impact`，展示后再确认）。楼盘停用是全后台确认体验的最佳范例，OPT-030 §3 已明文标注。

**更优方案**：把「楼盘停用」那套范式提炼成一个共享的**文档动作条**（`beforeDocumentControls` 挂载，输入是状态机定义 + 影响面查询 + 确认文案），然后逐个对象接上去。举报与纠错要先补 endpoint。这一条做完，M1 涉及的 7 个对象一次性收口。

### M2 两套列表 UI，能力与数据量成反比

| | Arco 自定义列表 | Payload 原生列表 |
|---|---|---|
| 页面 | 房源(2.2k) · 楼盘(83) · 城市 · 审计日志 · 审核台 | 线索 · 客户 · 商户 · 待办 · 通知 · 投放申请 · 用户 · 角色 · 举报 … |
| 批量选择 | **无** | 有 |
| 列排序 / 列自定义 | 无 / 无 | 有 / 有（「列」按钮） |
| 筛选形态 | 顶部下拉，写 URL | 「过滤条件」弹层 |
| 行内操作列 | 有（编辑 / 前台 / 详情） | 无 |
| 每页默认 | 25 | 10（商户 25、素材库 10） |

后果：**最大的两张表反而不能批量操作**。2 229 条房源要批量下架、批量取消推荐，没有复选框；3 条商户有全套批量能力。同一件事两种手势，分页默认值 10/25 混用。

**更优方案**：不推翻任何一边。给 Arco 列表补三件事——行选择 + 批量动作条（接 M1 的共享动作条）、列排序、可保存的筛选条件集（现在的深链 Tag 已是雏形）。统一每页默认值。

### M3 一件事，多处保存，各有各的版本号

- **商圈**：基础字段在抽屉或原生表单（`/api/locations` 乐观锁）、空间扩展在内嵌面板（独立「保存更新」+ 独立版本号，`/api/business-area-extensions`）、封面在弹层。改完一轮不知道该点几次保存、哪次没生效。
- **地铁线路**：站点拖拽排序后点「保存排序」，逐条串行 PATCH，逐行显示成败。
- **房源媒体**：媒体工作台在表单内，但走 Payload 行级 action，与文档保存是两条路径。

**更优方案**：内嵌面板的保存并入文档保存流；做不到时，在文档保存按钮旁显式标注「本页有 N 个独立保存区」。

### M4 只读字段淹没可操作字段

| 页面 | 结构 | 真正每天要改的 |
|---|---|---|
| 咨询线索 | 7 tab，约 25 个只读字段集中在后 3 tab | 姓名 / 电话 / 阶段 / 负责人 4 个，还分散在 tab1 与 tab3 |
| 投放申请 | 3 tab，其中「溯源与合规」全只读 | 「审单与补录」1 个 tab |
| 房源 | 「状态（只读）」+「数据来源」两节 | 与录入项混在同一列 |
| 审核记录 | 整个文档只读 | 无 |

**更优方案**：把「存档/溯源」类 tab 折到最后并默认折叠；把状态与负责人提到 **sidebar**——而全后台 31 个 collection **只有 `AuditLogs` 用了 `position: 'sidebar'`**，右列长期空置，这是最省力的一处结构红利。

### M5 内容没有草稿，也没有预览

- `Pages` 与 `Articles` **都没有 `versions: { drafts: true }`**（已核实）。`status: draft/published` 只是普通 select，**保存即改线上数据**，无草稿预览、无版本回滚，`publishedAt` 手填。
- `Pages` 的 `preview` **只对 `slug=home` 生效**（`Pages.ts:36`），其余页面无预览。
- 改首页文案要走：导航 → 站点设置 → 切 tab → 改 → 保存 → **另开前台标签页自查**，约 5–6 步。
- 全后台唯一有效的所见即所得是水印实时预览（参数随表单变化，不必先保存）。

**更优方案**：打开 drafts + preview 覆盖全部 slug，是内容侧性价比最高的一步。房源与楼盘已有 livePreview（三档断点），Pages/Articles/SiteSettings 照抄即可。

### M6 高危动作与普通字段同权重

- **城市上下线**：`CitySiteProfiles.serviceStatus`（已开通 / 筹备中）实质是把一个城市从前台摘下来，却是个普通 select，无确认、无影响面。
- **经纪人/团队停用**：`delete: () => false`，下线只能改字段保存；`protectBrokerStop` 在**提交后**才报「仍有未完成线索」。
- **水印全量重刷**：`WatermarkRebakeButton` 无二次确认，只有一句「可能要跑一会儿」，无批次 ID、无进度、无回执。1.7 万条素材。
- **改 media 的 `usage` 后重刷不会反烘焙**——这条不可逆语义只写在代码注释（`Media.ts:102`），UI 上完全看不到。

**更优方案**：同 M1，共享动作条统一承载「影响面预算 → 确认 → 结果回执」；把提交后才报的守卫改成进入表单时就展示的前置提示。

## 6. 更优方案：四个共享机制 + 三个结构补口

不是 43 页各修各的。按投入产出排序：

| # | 做什么 | 一次性覆盖 | 量级 |
|---|---|---|---|
| **A** | **共享文档动作条**：以楼盘停用为范式，抽出「状态机定义 → 影响面查询 → 确认 → 乐观锁提交 → 结果回执」的通用组件，挂 `beforeDocumentControls` | M1 的 7 个对象、M6 的 4 处高危动作 | 大 |
| **B** | **补两个缺失的 endpoint**：`listing-reports/:id/transition`、`information-corrections/:id/transition` | 让举报与纠错从「不可处理」变成「可处理」 | 中 |
| **C** | **Arco 列表补齐**：行选择 + 批量动作（接 A）+ 列排序 + 可保存筛选集 + 统一每页默认值 | 房源/楼盘/城市/审计 4 个大表 | 中 |
| **D** | **启用 sidebar**：状态、负责人、版本、溯源移入右列 | 房源、楼盘、线索、投放申请 | 小 |
| **E** | 打开 `drafts` + preview 覆盖全 slug | Pages、Articles，间接改善 SiteSettings | 小 |
| **F** | 角色权限三层改为按注册表分组的多选（编码 + 中文名同屏），保存前给能力 diff | 角色页，连带用户权限预览 | 中 |
| **G** | 补 `create` 到地理四模块（`GeographyCreateView` 已参数化）；审核台加「队列 / 全部记录」双 tab；城市列表行名做成详情链接 | M7 的三个缺口 | 小 |

先做 A+B 能把「有状态机无操纵杆」这条主线一次性掀掉，这是运营效率上最大的一块。D 与 E 是小改动大收益，可以并行。

## 7. 实施切分：按域纵切，不按层横切（2026-09-10 裁定后改写）

§6 的 A–G 是**机制**，不是工作项。用户裁定：后台任务要综合考虑、不按层拆——按层切会让同一个页面被改多次（先动作条、再右栏、后列表，动作条位置跟着返工）。
改为**按域纵切**：一个域一次把导航入口、工作列表、工作站、动作条、队列做到位，运营实际走一遍即可验收。
