# Task Packet：OPT-054 主导航与页脚分组后台可配（含路由池约束）

> 状态：**设计草案，未实施**
> 创建日期：2026-08-26
> 来源：从 `OPT-053` 拆出——用户 2026-08-26 裁定导航配置单独一轮
> 编号说明：OPT-053 是运营内容后台化，本项是它拆出的第二半
> **前置依赖**：`OPT-053` 的 `SiteSettings` Global 与迁移先落地。见 §5。

---

## 1. 一句话

主导航六项与页脚三组全部硬编码在 `public-nav.ts`，加一个入口、调一次顺序
都要发版；但**直接把 `href` 开放给运营填，等于开一座静默死链工厂**——
这一轮的真正内容是那套约束，不是那张表。

## 2. 证据

```ts
// src/lib/frontend/public-nav.ts:22
export const MAIN_NAV_ITEMS: readonly PublicNavItem[] = [
  { href: '/listings', label: '找办公室' },
  { href: '/buildings', label: '找楼盘' },
  { href: '/listings?type=coworking', label: '共享办公' },
  { href: '/entrust', label: '委托找房' },
  { href: '/publish', label: '投放房源' },
  { href: '/news', label: '资讯' },
] as const

// src/lib/frontend/public-nav.ts:32
export const FOOTER_COLUMNS: readonly PublicNavColumn[] = [ /* 浏览 / 按类型 / 服务 三组 */ ]
```

该文件的注释已经记下一条真实教训：调整前「服务式办公」在导航与页脚**各写了一份**，
改了一处忘了另一处。收敛到单一数据源是对的——本工作项要做的是把这个
单一数据源从代码挪到后台，**且不能把它重新变成两份**。

## 3. 核心难点：`href` 不能自由填

导航项的 `href` 指向真实路由。做成文本框，运营填错的后果是：

- Next.js 对不存在的路由渲染 404，**不抛异常、不进日志告警**；
- 页脚死链尤其隐蔽——没人天天点页脚，可能几个月无人察觉；
- 带参路由（`/listings?type=coworking`）的参数值绑定 `Listings.listingType`
  枚举，填一个不存在的枚举值不会 404，会**返回空结果页**，比 404 更难发现。

这与 `OPT-053 §4.4` 对 `typeCards.type` 的处置是同一判断：
**枚举与路由归代码，展示归运营。**

## 4. 设计：预设路由池 + `select` + 过期守卫

### 4.1 路由池

代码侧维护 `ALLOWED_NAV_TARGETS`，每项含 `id` / `href` / `defaultLabel`：

- 静态路由：`/listings`、`/buildings`、`/entrust`、`/publish`、`/news`、`/city-partner`
- 带参模板：`/listings?type=<listingType 枚举>`，选项由枚举生成而非手写

### 4.2 后台字段

`SiteSettings` 加两个 `array`：`mainNav`、`footerColumns`（后者嵌一层 `links`）。
每个导航项：

| 字段 | 类型 | 运营可改 |
|---|---|---|
| `target` | select（选项来自路由池） | ✅ 选，不能填 |
| `label` | text（默认取 `defaultLabel`） | ✅ |
| `visible` | checkbox | ✅ |
| 顺序 | array 拖拽 | ✅ |

**运营不可改：目标 URL 本身。** 新增路由目标需要发版。

### 4.3 过期守卫（本工作项最关键的一条）

路由池会静默过期：新增了页面，忘了加进池子，运营就配不出入口，
而**没有任何东西会提醒**。

`OPT-049` 就是这么烂掉的——`custom.scss` 里隐藏原生导航的选择器写的是
Payload 2 的类名，在 3.86 下一个都匹配不到，CSS 选择器匹配不上不报错，
于是那段死代码在线上挂了很久没人发现。

因此必须在 `tests/` 加双向守卫：

| 方向 | 断言 |
|---|---|
| 池 → 路由 | 池子里每个 `href` 都能解析到一个真实路由 |
| 路由 → 池 | `(frontend)` 下每个顶层公开路由，要么在池子里，要么在显式豁免名单里 |

第二条是防过期的那一条，**不能省**。豁免名单要求写理由，
否则它会退化成"往里塞就绿了"。

### 4.4 兜底

Global 无值 → 回落到 `public-nav.ts` 的现有常量。
常量**保留不删**，它同时是默认值来源与迁移前的兜底（与 `OPT-053 §5.2` 同构）。

## 5. 与 OPT-053 的耦合

两者都往 `SiteSettings` 加字段。**本工作项的迁移必须在 OPT-053 的迁移之后生成**，
否则同一张表的两条迁移会在快照链上打架（`OPT-048` 迁移快照链漂移在册未解）。

## 6. 明确不做

| 不做项 | 理由 |
|---|---|
| 自由填写 `href` | §3 全部理由 |
| 运营自建路由目标 | 目标必须对应真实页面，那是发版的事 |
| 导航项的图标 / 徽标配置 | 当前设计没有这些视觉元素，不为假想需求建字段 |
| 逐城导航差异 | 七城共用一套导航是现状，没有需求要拆 |

## 7. 未决

- 页脚分组的**组标题**（`浏览` / `按类型` / `服务`）是否也开放配置。
  倾向开放——它是纯文案，没有 `href` 的死链风险。
- 主导航项数上限。现在是 6 项，视觉上塞不下更多；
  是否要在后台加 `maxRows` 硬限制，还是靠运营自觉。倾向加硬限制。
