## 3. 走查发现（已取证，2026-08-16）

环境：本地 `master @ 00dd226`，Chromium 1280×720，账号 `e2e-adm`。

### 做得好的（作为模板，勿回退）

| 场景 | 机制 |
|---|---|
| **楼盘停用** | 二次确认 + 说明后果 + **实时算出影响面**："停用后该楼盘在 C 端不再展示，其下房源的审核/发布状态保持不变。当前无对外可见房源受影响。" |

**停用那条是全场最佳范例，做到了确认 / 讲清后果 / 量化影响面三层，建议作为其它高风险操作的模板。**

### P0-1 配套「清空已选」无任何确认

`AmenitiesChipSelector` 的「清空已选 (14)」点击后 14 个配套立即全灭，无弹窗、无撤销、无 Toast。与旁边"逐个点选"的操作成本完全不对称——误点一次要手工重选 14 次。

修法：加 Popconfirm 写明数量，或改为带撤销的 Toast。

### P0-2 表单改动后离开无拦截，改动静默丢失

实测：清空 14 个配套 → 站内跳转到列表页 → 无任何提示，改动全部丢失。

控制台印证：

```
Blocked attempt to show a 'beforeunload' confirmation panel for a frame
that never had a user gesture since its load.
```

`beforeunload` 有注册，但**站内路由跳转不触发它**，而后台绝大多数跳转都是站内跳转。这是最容易造成真实工作损失的一条。

修法：在 `isModified` 时接管路由跳转并弹确认。

### P1-1 后台首页存在服务端报错（独立缺陷）

```
TypeError: Cannot read properties of undefined (reading 'id')
  revalidating cache with key: getHomepage(...)-homepage,shanghai-[]
```

C 端首页缓存重建时报错，出现两次，未阻断后台。**与本工作项的交互改造无关，建议单独立项**，此处仅记录取证。

### P1-2 大量按钮无可访问名

楼盘编辑页有 **13 个按钮既无文本也无 `aria-label`**，包括媒体卡片的删除按钮。对"删除"这类操作，这本身就是防呆缺口。

### P1-3 确认弹窗不接管焦点

媒体删除的 Popconfirm 弹出后 `focusInsidePopup: false`，且无 `role` / `aria-modal`。键盘用户 Tab 会走到弹窗外，读屏不播报。

### P2 拖拽上传区键盘不可达

`tabIndex: -1`、无 `role`。但「批量上传媒体」按钮可达，功能有替代路径，故非阻断。

## 4. 「前台可见性」前置提示

### 4.1 问题

前台是否展示由 12 条判据决定（`.agent/supply.md`），但编辑时全部不可见。运营的真实体验是：**填完、保存成功、审核通过，前台还是没有**，界面从头到尾没给过线索。

CI 里那句注释是同一个坑的另一种表现：`gallery < 3 → 有效供给精筛 §6 排除全部房源 → 前台 0 套`。

### 4.2 关键发现：判据服务已经会返回排除原因

**不需要新写"返回失败原因的变体"**——`src/domain/review/effective-supply.ts` 已导出：

- `EFFECTIVE_SUPPLY_EXCLUSION_CODES`（排除码枚举）
- `EffectiveSupplyResult`（含排除码的结果结构）
- `isListingEffectivelySupplied()`
- `MIN_EFFECTIVE_MEDIA = 3`

`.agent/supply.md` 要求"所有消费者复用同一有效供给服务"，本卡片必须调用它，**不得自拼判断**，否则口径会漂移。既有导出已足够，这条约束不构成额外成本。

另有 `checkListingCompleteness()` 返回 `missing: MissingItem[]`，每项带 `field` / `label` / `reason`，`field` 注释明确写着"供前端定位高亮"——**为本需求预留的能力，此前只在提交审核时用**。

### 4.3 分层交付

**第一层｜编辑页常驻「前台可见性」卡片**（性价比最高，可独立上线）

复用 `EffectiveSupplyResult` 的排除码 + `MissingItem` 的 `field`，在房源编辑页侧栏常驻：

```
前台可见性：✗ 暂不可见
  ✓ 已上架    ✓ 审核通过    ✓ 未被举报
  ✗ 有效图片 2/3            ← 点击定位到媒体区
```

**每条必须可点击跳到修复位置**，而不只是报错。楼盘编辑页的 `BuildingAggregateCard` 已有位置与样式可沿用。

范围限自身条件（发布状态 / 审核状态 / 举报暂停 / 媒体数），跨对象条件不纳入（见 §2）。

**第二层｜保存后按结果反馈**

保存成功但仍不可见时，Toast 说明主因："已保存。前台仍不可见：还差 1 张有效图片。"——避免"保存成功"被误读为"已上线"。

**第三层｜提交审核前置校验补齐**

`checkListingCompleteness` 的 `submit` 模式已覆盖房源自身字段。本层仅确认其与可见性卡片口径一致，不扩范围。

## 5. 建议优先级

按修复性价比：

1. **P0-2 离开拦截**——小改动、防止真实工作损失
2. **P0-1 清空确认**——小改动
3. **第一层可见性卡片**——中等改动，直接消除"保存成功却不显示"的困惑
4. P1-2 按钮可访问名 / P1-3 弹窗焦点
5. 第二层 Toast
