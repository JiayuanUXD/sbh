## 1. 产品目标与成功标准

### 1.1 目标

让首次到访用户在不登录的情况下快速理解 SBH 的服务、找到可比较的真实房源，并以低压力方式完成一次有效咨询；同时为复访用户保留收藏、历史和咨询进度的后续扩展位置。

### 1.2 MVP 成功标准

- 用户进入首页后可以立即搜索或使用快捷筛选，首屏后半段能够看到真实房源，而不是只看到品牌叙事。
- 用户可以在同一计价单位内筛选和比较房源；系统不跨单位换算、聚合或排序。
- 房源详情明确展示月租估算、物业费包含状态和预计月度占用成本，并说明计算条件：已包含不重复加总；不包含仅在租金、物业费金额和面积齐全时加总；待确认或缺失时不展示合计。
- 用户能从详情页完成咨询；提交具备幂等、隐私同意、失败重试与明确反馈。
- Web 与小程序针对同一城市、同一时点解析出的公开房源 ID 集合一致。
- 首个纵向闭环通过微信开发者工具模拟器与至少一台真机验收。

## 2. 范围

### 2.1 MVP 页面

1. 首页
2. 城市切换
3. 房源列表、搜索与筛选
4. 房源详情
5. 楼盘列表与名称搜索
6. 楼盘详情
7. 咨询提交与结果页
8. 加载、空、错、失效、已出租/已下架等状态页

### 2.2 首个实施批次

只接通上海的房源纵向闭环：

```text
首页
  → 搜索 / 快捷筛选
  → 房源列表 / 完整筛选
  → 房源详情
  → 咨询提交
  → 成功或可恢复失败
```

楼盘页面、收藏和个人中心在这个闭环稳定后接入，避免同时建设大量页面却没有一条真实可验收链路。

### 2.3 非目标

- 地图找房、通勤时间计算
- 房源对比器
- 求租广场或公开 UGC
- 跨设备浏览历史与消息通知
- 线上预约看房排期
- 自动轮播、逐卡 500ms 滚动进场等装饰性动效
- 多端框架与 H5/WebView 复用
- 小程序直接写 Payload Collection 或在客户端组合领域事务

## 3. 体验与视觉设计

### 3.1 首页信息层级

采用“品牌 + 效率”双层结构：

1. 160–180px 的短品牌头图，说明“SBH 能帮用户找什么”。
2. 搜索框与高频快捷筛选立即承接任务。
3. 第一组真实房源尽量在首屏下沿出现。
4. 信任、服务流程与品牌内容后置，不阻塞找房主路径。

首页不放“求租广场”。商办需求包含公司、预算、位置和扩张计划等敏感信息，公开展示的信任成本高，也会分散首次用户的搜索任务。

### 3.2 基础视觉

- 页面底色 `#f2f2f4`，白色卡片分组。
- 内容卡圆角 8px；图片和输入框 6px；小标签 3px。
- 中性灰承担信息层级，蓝色只表达可交互元素，不给价格、等级或普通标签添加装饰性色。
- 有意义的小字至少使用 `#6e6e73`；`#86868b` 仅用于占位符和禁用态。
- 中文保持自然字距，数字使用等宽数字。
- 触控目标不小于 44×44px，相邻操作间距不小于 8px。

小程序保留参考稿的紧凑、轻量和熟悉感，但不机械同步 Web 的 18px 卡片圆角与桌面留白；二者共享品牌原则和语义，不要求共享相同像素值。

### 3.3 房源列表与筛选

- 首屏提供“价格”等高频快捷筛选，完整条件进入底部筛选面板。
- 计价单位是结果集维度，必须显式显示；切换单位等于切换结果集。
- 价格、面积、区域、商圈、地铁、类型等条件改变时回到第一页。
- 无结果时给出可执行退路，例如逐项放宽条件，而不是只展示“暂无结果”。
- 房源卡主信息为：月租估算、面积、位置、类型；单位报价作为次级信息。
- 卡片按压反馈 120ms 左右；抽屉和状态切换 160–240ms；首屏加载使用骨架屏。

### 3.4 房源详情与转化

- 决策信息优先于长篇介绍：月租估算、物业费、预计月度占用成本、面积、可用日期和位置在前。
- 月度成本必须标注计算条件；缺少必要字段时显示“—”或拆项，不伪造合计。
- 主按钮使用“咨询顾问”或“获取完整报价”，降低首次用户对“预约看房”的承诺压力。
- “预约看房”在具备排期、顾问分配和通知能力后再作为次级能力。
- 可信度文案使用“核验于 YYYY-MM-DD”与“发现失效”，不使用无法保证的“实时同步”。
- 房源已出租、失效或下架时保留事实说明，并提供相似房源入口，不让用户落入死路。

### 3.5 楼盘与个人能力

- 楼盘列表必须提供楼盘名称搜索；楼盘详情聚合公开有效房源。
- 匿名用户可以完整浏览。收藏、咨询记录等需要身份的功能在用户触发时调用 `wx.login`。
- 手机号仅在咨询提交阶段获取；用户拒绝授权时允许手工输入，不阻断咨询。

## 5. 服务端与 API 边界

### 5.1 总体结构

```text
微信小程序
  → HTTPS /api/mini/v1/*
    → Mini API route + DTO mapper
      → Public Catalog / Effective Supply / Inquiry domain service
        → Payload Local API + PostgreSQL
```

- 路由建议放在 `payload-office-platform/src/app/api/mini/v1/`。
- API 门面负责传输协议、参数校验、身份适配、响应版本和公开 DTO 映射。
- 页面和小程序组件不接收原始 Payload Document。
- API 门面不复制有效供给谓词，不以 `status=available` 等简化条件降级。
- 公开 DTO 默认不包含内部电话、商户资质、审核、举报、权限和审计字段。

### 5.2 MVP 端点

| 方法与路径 | 用途 |
|---|---|
| `GET /api/mini/v1/home` | 城市首页、快捷筛选、精选房源与信任信息 |
| `GET /api/mini/v1/listings` | 房源搜索、筛选、排序、分页与各单位计数 |
| `GET /api/mini/v1/listings/:slug` | 房源详情及相似房源 |
| `GET /api/mini/v1/buildings` | 楼盘列表与名称搜索 |
| `GET /api/mini/v1/buildings/:slug` | 楼盘详情及其有效房源 |
| `POST /api/mini/v1/session` | `wx.login` code 换服务端会话 |
| `POST /api/mini/v1/inquiries` | 咨询提交，复用咨询领域逻辑 |

### 5.3 DTO 与错误协议

- 价格字段必须携带币种、租售类型、周期、计价基础和展示单位。
- 列表响应必须返回 `items`、分页信息、当前筛选、可选项计数与 `asOf`。
- 所有响应包含稳定的业务错误码和 `requestId`；客户端不依赖后端中文报错做分支判断。
- 404、已失效、已出租、频率限制、会话过期、校验失败和服务暂不可用分别建模。
- API 版本不在客户端隐式猜测；不兼容变更发布 `/v2`，`/v1` 在迁移期保持可用。

### 5.4 缓存与一致性

- Public Catalog 数据快照在服务端 `unstable_cache` 中最长缓存 5 分钟，响应 `meta.maxAgeSeconds=300` 表示这层数据快照 TTL，并携带真实数据时点 `asOf`。
- HTTP 响应统一 `Cache-Control: private, no-store`。响应含调用方 `requestId`，不得被共享缓存或浏览器持久缓存；缓存复用和标签失效只发生在内部数据快照层。
- 上架、下架、冻结、举报暂停、商户失效等领域事件触发缓存失效。
- Web 与小程序共用 Public Catalog 与 Effective Supply，不建立第二套查询口径。
- 小程序图片 URL 必须由 API 使用受信任 `siteOrigin` 将根相对 `/media/...` 转成绝对 URL；已是绝对地址的 CDN URL 原样保留，生产配置保证 HTTPS。

## 6. 身份、安全与隐私

- 浏览默认匿名，不在 `App.onLaunch` 请求头像、昵称或手机号。
- `wx.login` 的 code 只传给服务端；服务端换取并保存会话，小程序不保存 AppSecret。
- AppSecret、小程序上传私钥、数据库凭据和第三方服务密钥不得进入仓库。
- 会话使用短期 token，服务端校验过期、撤销和频率限制；客户端角色和城市范围不可信。
- 咨询提交复用现有领域 schema、幂等和审计逻辑，但使用适合小程序的身份/防滥用适配器。
- 不通过放宽现有 Web `/api/inquiries` 的同源或 CSRF 守卫来兼容小程序。
- 手机、IP、设备标识等敏感字段遵循最小采集、服务端脱敏和用途说明。
- 提交前展示隐私同意；服务端记录政策版本、来源路径、requestId 与幂等键。

## 7. 环境、工具与发布

| 环节 | 工具与责任 |
|---|---|
| 代码、重构、单元测试 | Codex + Git 分支/worktree |
| 模拟器、网络面板、分包与性能 | 微信开发者工具 |
| 组件测试 | `miniprogram-simulate` |

开发、预发布、生产使用各自的 HTTPS API 域名；域名加入微信后台合法域名白名单。预发布环境使用脱敏测试数据，不让开发版小程序直连生产写接口。

仓库当前要求 Node 22.x；本机基线检查实际为 Node 24.14.0。正式开发前统一到 Node 22，避免依赖安装、开发者工具构建和 CI 结果漂移。

## 8. 质量与验收策略

### 8.1 自动化

- 小程序纯函数与状态映射单元测试。
- 组件正常、加载、空、错、禁用和长文本状态测试。
- API schema、DTO mapper、权限、限流、会话和幂等测试。
- Web 与小程序公开供给一致性测试：相同输入下 Listing ID 集合一致。
- 纵向闭环自动化：进入首页、筛选、打开详情、提交咨询、验证结果。

### 8.2 真实环境验收

- 微信开发者工具检查请求、分包大小、首屏加载、错误日志和缓存行为。
- iOS 与 Android 至少各一台真机覆盖 375px 左右小屏和常见大屏。
- 覆盖弱网、超时、离线恢复、图片失败、会话过期、重复提交和服务端错误。
- 核心流程全键盘不是小程序主要场景，但语义、焦点、读屏文案和 44px 触控目标仍按 WCAG 2.2 AA 原则检查。
- 现有 Web 链路继续守住 p75 LCP ≤2.5s、INP ≤200ms、CLS ≤0.1；小程序发布门使用微信开发者工具可复核的启动耗时、首屏渲染与交互响应指标，不把 Web 指标生搬到小程序运行时。

## 10. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 参考稿字段与真实数据不一致 | M0 用真实 DTO 样本制作状态矩阵，不以静态假数据验收 |
| 小程序与 Web 供给口径分叉 | 共用领域服务，并建立 Listing ID 集合一致性测试 |
| 咨询接口为兼容小程序而削弱 Web 安全 | 独立 Mini API 身份适配，复用领域逻辑而非放宽 Web 守卫 |
| 微信合法域名或资质晚准备 | M1 前确认 AppID、合法域名、类目和隐私声明；开发阶段使用独立预发布域名 |
| 页面先铺开、闭环长期不可用 | M2 只做上海纵向切片，验收后再扩展页面族 |
| 依赖环境漂移 | Node 22 与锁文件统一，CI 和本地使用相同版本 |
| 首屏图片过重 | 明确尺寸、压缩与占位，按可视区域加载，开发者工具持续检查包体和请求 |

## 11. 本任务包验收门

- 用户确认页面范围、首个纵向闭环、目录结构和 API 边界。
- 用户确认首页“品牌 + 效率”层级及详情页以低压力咨询为主转化。
- 文档中无待填字段、隐含的跨单位换算或直接 Payload REST 调用。
- 后续实施计划必须拆分为独立工作项，不在一个任务中同时修改小程序工程、Mini API、身份、数据库和发布配置。
- 未经用户确认，不提交、推送、创建 PR、部署或执行数据库迁移。
