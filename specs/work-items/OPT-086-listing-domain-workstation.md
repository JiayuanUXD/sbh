## 1. 一句话

房源是生产里唯一在日常运转的域（2 229 条，近 30 天 18 次更新，审核记录 4 213 条）。本项一次把它做到位：
列表变工作列表、编辑页变工作站、动作条补齐发布轴、可见性卡能回答「为什么前台看不到」、
楼盘商户关系不再 18 次点击。运营走一遍「让一套房源在前台可见」的全流程就能验收。

## 2. 为什么按域切，不按层切（记录裁定）

084 说房源列表要并进「房源与楼盘」组，085 说它缺批量、编辑页缺右栏，086 初稿说它缺下架动作——
三份文档说的是同一个页面。按层切（先动作条、再右栏、后列表）会让这个页面被改三次，动作条位置还要跟着右栏返工。
按域切，一次交付，运营实际走一遍即可验收，符合宪章「完成前必须在浏览器里实际走一遍」。

**唯一例外是导航**：它是单个配置文件，分域改会让导航长期处于中间态，整体一次改（084 Phase 1）作为本项前置。

## 4. 目标体验：一条主线闭环

运营视角，「让一套房源在前台可见」在一个域内走完：

1. 在**楼盘页**看到并补齐商户关系，不再跳三个分组
2. 在**房源列表**按状态分段看队列，能批量处理
3. 在**房源工作站**右栏看状态与健康度，顶部动作条改状态，主列只做录入
4. **可见性诊断**一处回答「为什么前台看不到」，每条原因带修复链接
5. **审核台**是同一条流水线的判定站，不再截断在 200 条

## 5. 设计

### 5.1 房源列表 → 工作列表

- **状态分段**（segmented，带计数）：全部 / 草稿 / 待审核 / 已上架 / 待复核 / 已下架 / 已出租。分段写 URL 参数，可分享可后退。
  「待审核」「待复核」这两个今天藏在筛选下拉里的队列变成显性入口；审核台与「待审核」分段共享同一 `where`，
  这就是 085 F5「一物一入口」的落地：**审核台 = 待审核分段的判定视图**，不再是另一套口径。
- **行选择 + 批量条**：批量下架（一次填原因，逐条提交）、批量取消推荐 / 设为推荐。**不做批量上架**（必须走审核）。
  批量走既有单条端点逐条提交、逐行回执（沿用 `MetroLineStationsPanel` 的逐行成败模式），不新造批量端点。
- **排序**：更新时间 / 面积 / 价格三列可排（现在固定 `-updatedAt`）。
- **新增「前台可见」列**：绿 / 灰 / 红三态点，来自 §5.4 的诊断；点开即诊断抽屉。
- **命名筛选**：把今天的深链 Tag（`missingCover` / `pendingRecheck` / `building`）泛化为命名筛选芯片：缺封面 / 待复核 / 无供给商户 / 商户资质将到期。**只存 URL，不入库**。
- **每页统一 25**：原生列表的 10 顺带改成 25（`admin.pagination.defaultLimit`），全后台一个数。

### 5.2 房源编辑页 → 工作站

三区布局，Payload 原生能力即可，不引新组件：

| 区 | 内容 | 机制 |
|---|---|---|
| 顶部文档控件 | 动作条 + 保存 | `admin.components.edit.beforeDocumentControls` |
| **右栏 sidebar** | 状态卡（审核 / 发布 / 冻结 / 版本，沿用 `ListingReadonlyValue`）→ 可见性诊断卡 → 完整度卡 → 供给商户 / 联系经纪人 → 数据来源（默认折叠） | 逐字段 `admin.position: 'sidebar'`；`ui` 字段同样可进右栏。先例：`AuditLogs` |
| 主列 | OPT-032 定下的两个 tab 原样；去掉「审核与发布」「状态（只读）」「数据来源」三节 | 只删节，不动其余行 |

右栏在两个 tab 下都可见——切到「展示内容」时状态不丢，这是它比放主列强的根本原因。
那个叫「审核与发布」却既不能审核也不能发布的节名随之消失。

主列净减两节，高度朝 OPT-032 的 1 735 目标再降一截；本项完成后按 OPT-032 同一口径（离屏克隆）复测一次并回写数字。

### 5.3 动作条（共享组件第一版）

形状固定为：`availableActions(状态, 权限) → 确认（含后果） → 提交（expectedVersion） → 回执`。

动作矩阵以 `canTransitionPublication`（`domain/review/publication-status.ts:88`）与审核端点为**唯一事实源**，客户端矩阵用单测钉死不漂移；不可用的动作**不渲染**，不是禁用。

| 当前发布态 / 审核态 | 动作 | 权限 | 确认内容 |
|---|---|---|---|
| 草稿 | 提交审核 | 沿用审核端点既有判定 | 展示完整度缺项（复用 `checkListingCompleteness`） |
| 待审核 | 撤回 | 同上 | 二次确认（今天审核台的撤回没有，本项补齐） |
| 待审核（具 `listing:review`） | 通过 / 驳回 | `listing:review` | 与审核台**共用同一确认抽屉组件** |
| 已上架 | **下架** | `listing:unpublish` | **原因必填**，为空时确认按钮禁用，不拿 422 当校验 |
| 已上架 | **标记已租** | `listing:publish` | **明写「将同时撤销首页推荐」**——端点里的隐藏副作用（`listing-publish-endpoint.ts:172-177`）必须让人看见 |
| 已下架 / 已出租 | 重新上架 | `listing:publish` | 提示「需满足有效供给条件才会真正出现在前台」，链接到诊断卡 |

回执：成功 `Message.success` + `router.refresh()`，右栏状态与诊断同步刷新；`ILLEGAL_TRANSITION` 把端点中文文案原样展示；版本冲突提示「本页数据已过期，请刷新后重试」，不静默覆盖。

**第一版只服务房源，不做通用抽象。** 一个样本抽不出对的抽象；第二个对象（风控域的举报）接入时再抽通用层。这条要写进代码注释，防止下一个人上来就泛化。

### 5.4 可见性诊断（本项最有价值的一条）

现状：可见性卡只看房源自身 4 项，自己写明「商户 / 楼盘 / 服务城市等关联条件未包含在内」。有效供给服务分两层——查询层谓词（§1–§4、§7）藏在 `getEffectiveSupplyWhere` 的 where 里，解析层 `isListingEffectivelySupplied` 只返回两个码且 §8 短路（`effective-supply.ts:143-180`）。**没有一处能说出「这套房源到底为什么前台看不到」**。

设计：新增领域函数 `diagnoseListingVisibility(listingId, asOf)`，逐条跑 `.agent/supply.md` §1–§12（§6、§8 的旧口径已废除，按现行口径）：

| 谓词 | 判定来源 | 运营文案 | 修复链接 |
|---|---|---|---|
| §1 未逻辑删除 | 文档 | 房源已删除 | 回收站 |
| §2 已上架 | 文档 | 未上架（当前：草稿 / 已下架 / 已出租） | 动作条 |
| §3 审核通过 | 文档 | 未通过审核（当前：待审核 / 已驳回） | 审核台 |
| §4 可见性正常 | 文档 | 待复核 | 动作条 / 复核入口 |
| §5 未被举报暂停 | `getPausedListingIds` | 被举报暂停 | `listing-reports?targetListing=` |
| §7 楼盘 / 城市 / 区域启用 | 反查 building.status、city.status | 楼盘已停用 / 城市未开通 | `buildings/:id` / 城市站点配置 |
| §8 已设置供给商户 | `NO_SUPPLY_MERCHANT` | 未设置供给商户 | 本页「供给商户」字段（`locateFormField`） |
| §9 商户启用且资质有效 | **拆开** `checkMerchantEligibility` 的子原因 | 商户已停用 / 资质无效 / 资质已过期 | `merchants/:id` |
| §10 服务城市覆盖楼盘城市 | 同上子原因 | 商户服务城市不含本楼盘所在城市 | `merchants/:id` |
| §11 可租且可用日期未结束 | 文档 | 可用日期已过 | 本页字段 |
| §12 未陈旧 | `domain/supply` 陈旧规则 | 超过 N 天未维护 | 动作条「确认信息仍有效」（若无此动作则提示更新） |

- 暴露为 `GET /api/listings/:id/visibility-diagnosis`（登录 + listings 读权限），返回 `{ visible, reasons: [{ code, section, label, href }] }`。
- 右栏可见性卡改为消费它；列表「前台可见」列用同一函数，**按 building / merchant 批量预取**避免 N+1。
- **守卫单测**：断言诊断覆盖的谓词编号集合 = supply.md 现行条目集合。以后加谓词漏诊断，这条会红——这是防止「诊断卡再次撒谎」的机制。
- `EffectiveSupplyResult.reasons` 的两个粗码保持不变（其它消费者在用），诊断函数在其外层组合，不改既有判定。
