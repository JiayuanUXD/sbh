# Task Packet：OPT-047 房源列表页缓存超 2MB 写入失败，`unstable_cache` 形同虚设

> 状态：**已验收**（2026-08-25，方案 1「收窄字段」；生产实测四条判据全绿，见 §6.6）
> 创建日期：2026-08-24
> 来源：2026-08-24 排查 OPT-046 时在生产容器日志里发现（顺带发现，与 job 泄漏无关）
> 编号说明：OPT-046 是 Jobs 事务泄漏，故取 047

---

## 1. 一句话

`/shanghai/listings` 的 `unstable_cache` 条目**超过 Next.js 的 2MB 上限，写入被拒**，
缓存永远建立不起来——这个路由的每一次请求都在真打数据库，`revalidate: 300` 完全没生效。

## 2. 证据（生产实测，非推测）

2026-08-24 生产容器日志（`sbh-107`，stderr）：

```
Failed to set Next.js data cache for unstable_cache
  /shanghai/listings?_rsc=P9NmyUiitymTZ9HH 72a2325b2c53f8f4090afa4a4e1802ba58c1eb22cad57666bce061978516d1fb,
  items over 2MB can not be cached (2278117 bytes)
```

2,278,117 字节 ≈ **2.17 MB**，超限 8.6%。

查询方法（容器名是**版本名**如 `sbh-107`，不是服务名 `sbh`，见 OPT-046 §6.5）：

```
queryLogs(action=searchLogs, service=tcbr, queryString='"can not be cached"',
          startTime=..., endTime=...)
```

## 3. 为什么这条比看起来严重

- **静默失败**。写缓存失败只打一行 stderr，页面照常 200 返回，响应时间也不会突变
  （单次查询本来就不慢），**没有任何外部信号**。它已经这样运行了多久无从得知。
- **失去的是保护而不只是速度**。`revalidate: 300` 的作用是把这个路由的 DB 压力
  压到「每 5 分钟一次」；写不进去等于**每个请求各打一次**。OPT-046 的故障里
  「首页还好、`/api/health` 已挂死」正是因为其它路由有缓存挡着——
  这个路由没有那层保护。
- **超限幅度很小（8.6%）**，意味着它大概率是**最近某次数据增长刚跨过阈值**的，
  且随着房源数量增长只会更超。反过来说，压下去也不需要大改。

## 4. 排查起点

`src/lib/frontend/cached-queries.ts` 里有十余个 `unstable_cache` 包装，
**先确认到底是哪一个**产出这 2.17MB——日志里的 hash 是 Next 派生的缓存键，
不能直接反推，建议在本地用同参数复现并量 `JSON.stringify(result).length`。

已知的相邻线索（同一文件内的注释，属于楼盘侧但形态相同）：

> 同一秒涌入的同 URL 并发请求在冷缓存下各跑一次 `searchBuildings`
> （同样是**不分页、`depth: 2`** 的那条查询）

「不分页 + `depth: 2`」是体积膨胀的典型成因：`depth: 2` 会把 relationship 整份展开
（楼盘、城市、商户、媒体…），不分页则一次性装下全量候选。房源侧若是同一形态，
就是主嫌。

## 5. 修法方向（未裁定）

1. **收窄字段**：列表页只需要卡片字段，用 `select` 明确列出，别整份文档进缓存。
2. **降 depth**：`depth: 2` → 按需展开，或改成只缓存 ID 列表 + 逐条走各自的缓存条目。
3. **分页/分片缓存**：把一大条拆成多条小的，天然规避单条上限。
4. **加体积守卫**：缓存写入前量一次大小，超阈值就打 `error` 级日志（当前只有
   Next 自己那行 stderr，无结构化字段、无法告警）。

方向 1 与 2 大概率能一次性把体积压到阈值以下，且不改变页面行为。

## 6. 验收

- 本地量出该缓存条目实际字节数，修复后 **< 1MB**（留足增长余量，别卡在 2MB 边上）；
- 生产日志中 `"can not be cached"` **不再出现**；
- `/shanghai/listings` 页面内容与分页/筛选行为无变化（e2e 覆盖）；
- 冷缓存后连续两次请求，第二次不再打库（可用 `pg_stat_activity` 或查询计数验证）。

## 6.5 实施记录

**根因定位（本地实测，不是推断）**：缓存的是 `buildListingSearchSource` 的**全量卡片
数组**（刻意设计，让 `?page=2` 不重跑最重的查询），所以体积 ∝ 房源数 × 单张大小。
本地量得每张 **2160 字节**，生产 1000+ 套 ≈ 2.16MB，与实测 2,278,117 字节吻合。

字段构成：`building` 1034（48%）+ `coverImage` 541（25%）= 73%。
其中 `blurDataURL`（约 480 字节 base64）**被存了两遍**——`card.coverImage` 与
`card.building.coverImage` 各一份。

**改动**（方案 1，用户裁定「只剔确实没人用的」）：

| 阶段 | 每张 | 生产推算 |
|---|---|---|
| 改动前 | 2160 | 2.16 MB ❌ |
| 剔 `building` 无用字段 | 1342 | 1.28 MB |
| 剔 `blurDataURL` | 886 | 0.84 MB |
| 保留 `coordinates`（见下） | **941** | **0.90 MB** ✅ |

`blurDataURL` 是**彻底的死重**：全仓只在 `Media.tsx` 的 props 类型里声明、
在 mapper 里赋值，**没有任何一处渲染它**。1000 张 × 480 字节 ≈ 480KB。

**一个我差点犯的错**：初版把 `building.coordinates` 也剔了，被
`opt035-homepage-stats` 那条测试抓住——首页「附近房源」在 **domain 层**用它算距离
（`facade.ts:983` 的 `haversineKm`）。我先前扫消费方只扫了 `src/components/frontend/`。

> **教训：扫「谁在用这个字段」不能只扫组件目录，domain 层也会读 DTO。**

**守卫**：`tests/listing-card-payload-size.test.ts` 7 条，断言单张 < 1200 字节
（改动后 941，留约 27% 余量）+ 不含 `blurDataURL` + `coordinates` 必须保留 +
剔字段没伤到卡片数据 + 封面兜底逻辑未坏。**双向验证**：把 `blurDataURL` 或完整
`building` 塞回来，立刻红。

**浏览器实测**：列表页 11 张卡片图全部有 src、楼盘名与价格正常；
首页「附近房源」距离正常渲染（2.6 / 5.4 / 6.7 km）。

## 6.6 生产验收（2026-08-25，版本 `be6f6a0`）

四条判据全部拿到，**每一条都在生产上实测，不是本地推断**。

### ① 日志：`"can not be cached"` 不再出现

| 窗口 | 容器 | 命中 |
|---|---|---|
| 部署前 14:23:20 / :26 / :30 | `sbh-110` | **3 条**，均为 2,278,117 字节 |
| 部署后 14:36–15:10 | `sbh-111` | **0 条** |

部署前那 3 条与我打基线的 3 次请求**时间戳一一对应**——即「每请求一次就写失败一次」。

> **零命中必须先证明日志通道是活的。** 同窗口用 `queryString: "*"` 查到 `sbh-111`
> 正常输出，才能把零命中当真阴性。否则查错容器名 / 查错窗口都会得到同一个「0」，
> 而那是假阴性（OPT-046 §6.5 那个坑的同一形态）。

### ② 响应时间：6.2s → 0.10s

| | 第 1 次 | 第 2 次 | 第 3 次 | 第 4 次 |
|---|---|---|---|---|
| 部署前（`sbh-110`） | 6.2s | 3.1s | 3.2s | — |
| 部署后（`sbh-111`） | 6.3s（冷，写入缓存） | **0.13s** | **0.10s** | **0.10s** |

部署前**每次都慢**（缓存从未写成功）；部署后只有第一次慢，之后 **31 倍**加速。
这同时验掉了 §6 第 4 条「冷缓存后第二次不再打库」——0.10s 不可能是打库的结果。

### ③ 页面内容无变化

| 页面 | 结果 |
|---|---|
| `/shanghai/listings` | 200 / 0.10s，24 张卡片，`blurDataURL` 与 base64 内联图 **各 0 处** |
| `/shanghai`（首页，`/` 307 跳转至此） | 200 / 0.12s，8 房源卡 + 8 楼盘卡，热门商圈 / 精选房源 / 资讯各区块完整 |

## 7. 坑

- **~~别用响应时间判断这个问题修没修好~~ —— 这条我写错了，已订正。**
  当时的依据是本地观察（夹具只有几十套，查询本来就快）。生产实测是 **6.2s → 0.10s**，
  差 31 倍，响应时间是**极其**明显的信号。
  真正成立的那半句是：**响应时间不能用来「发现」这个问题，只能用来「确认」它修好了。**
  发现不了是因为没有对照——一个一直 3 秒的页面，看起来就只是「有点慢」，
  没人会想到它背后是「缓存从未写成功」。**要判定必须冷热对照：连续请求两次，
  第二次仍慢 = 缓存没生效。** 这个对照本身成本极低，却是整条链上唯一的外部信号。
- **把本地观察当成通用结论，是这条错误的来源。** 本地夹具规模 ≠ 生产规模，
  凡是与「数据量」相关的判断，本地测不出来不等于生产测不出来。
- **2MB 是 Next.js 的硬上限，不可配置。** 只能把数据压小，不能调大阈值。
